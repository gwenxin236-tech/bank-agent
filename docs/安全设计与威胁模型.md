# 安全设计与威胁模型

## 1. 安全目标

T15 校准：本节是安全目标，不是对任意攻击或生产系统的保证。默认运行离线 Mock；当前实现与生产目标分列如下。权限来自 PolicyEngine，领域建议和模型输出均不是授权。验收记录及已知限制见 `docs/安全自评报告.md`、`docs/需求追踪矩阵.md`。

1. Agent 无法绕过服务端授权直接调用副作用工具。
2. 系统不会把未被银行工具确认的结果描述成成功。
3. 高风险金融操作必须拥有独立于模型的用户确认和强认证。
4. 输入中的外部文本、网页内容、附件或 IM 消息不能改变系统策略。
5. 所有关键动作可通过 trace_id 重放、审计和追责。

## 3. 权限分级实现

### 绿色

- 策略明确允许自动的查询直接执行；订阅查询虽只读，仍为黄色。
- 用户视图展示对应工具事实；不声称每种视图都已显示查询时间。
- 不允许因“查询”上下文衍生写操作。

### 黄色

- 按业务展示对应对象、金额、步骤和风险，非转账查询不虚构扣款字段。
- 执行入口是绑定 plan_id + action_token 的原计划确认，HTTP 会话须匹配身份/设备；不能把聊天中的“好的/继续”当作无条件授权。

### 红色

- 当前仅固定 OTP 演示：首次 confirm 发起 challenge，verify 通过后仍需再次 confirm；绑定摘要/身份/设备，有效期依 `config/policy.json:47/48`。未接真实短信、生物识别或 U-Key。
- 日累计越过黄色边界的转账及策略规定卡片操作等进入红色；不代表密码/投资等每种目标业务均已完整接入。
- 真实设备、地理/跨境风控与人工审核是生产替换点，不能只因架构写过就宣称已实现。当前来源/规则见 PolicyEngine 和测试。

## 4. 审计事件

下面是历史设计示意，不是当前 API 原始事件格式；实际事件为 `AuditStore.write` / `_event_from_row` 的 seq、prev_hash、current_hash、payload 等字段，工具成功事件名为 tool.result，来源见 `app/banking_agent.py:823/909/3526`。当前样本以 `/api/v1/audit/events` 输出为准，不使用此处旧版本号作为运行策略版本。

```json
{
  "trace_id": "trace_xxx",
  "actor": "user_xxx",
  "event_type": "tool_succeeded",
  "policy_version": "2026-09-18",
  "risk_level": "yellow",
  "intent": "transfer",
  "tool": "create_transfer",
  "input_hash": "sha256:...",
  "result": {"transaction_id": "tx_xxx", "status": "SUCCESS"},
  "created_at": "2026-09-18T00:00:00Z"
}
```

生产环境建议：写入 append-only/WORM 存储，日志内容分级加密，安全团队拥有只读检索权限，核心账务流水作为最终事实源。

## 5. 熔断与人工接管

- `config/policy.json:50` 的默认阈值为 3；认证错误与工具失败可增加运行时 CircuitBreaker 计数，锁定后拒绝其后请求。当前锁属于共享 runtime，不是已隔离的每租户/每会话锁；不能把可用性隔离当成已完成。
- 未知交易结果保留证据等待核实，不重发副作用，不承诺自动退款/冲正。没有普适的“所有超时自动降为只读”机制。
- 高风险规则可暂缓转账；未找到模型置信度阈值触发真人接管的实现证据。
- T09 本地队列仅登记、领取、固定结论和本人查询；handoff 的原 DAG 不自动恢复，未知结果只允许 NEEDS_RECONCILIATION。结单不修改银行交易状态，也不代表接通真人；新请求仍经过原权限链。见 `app/handoff_queue.py`、`docs/T09本地人工接管.md`。

## 6. 沙箱设计

日常金融业务使用固定工具。T07 新增独立 Docker 容器的受限计算代码演示：`python scripts/sandbox_qa.py`，复用 `AuditStore` / `CircuitBreaker`，执行无网络、只读根文件系统、非 root、资源/时长/输出配额和摘要审计。固定隔离探针供运维验收，不向聊天开放代码入口；详见 `docs/T07隔离执行演示.md`。该演示未接入真实 LLM 生成，也不代表任意敌对代码的生产隔离。

生产若加入更广泛的“自动生成报表/规则脚本”等能力，仍要求：

1. 代码在 gVisor、Firecracker microVM 或独立 Kubernetes Job 中运行。
2. 默认无网络、只读文件系统、CPU/内存/时长配额。
3. 通过 allowlist 允许少量库与函数；禁止 shell、反射、动态导入、文件系统和密钥访问。
4. 结果通过结构化协议回传；沙箱不能获得转账工具凭证。
5. 每次运行记录代码哈希、镜像哈希、输入输出摘要和租户信息。
