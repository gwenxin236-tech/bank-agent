# C8：健康检查与故障恢复演练

## 1. 交付边界

本任务验证**单进程、同一台机器、同一份 SQLite 文件仍然可用**时的进程崩溃恢复，使用 MockBankCore，全部离线、零第三方运行时依赖。不是生产灾备验收，不代表异地容灾、存储介质损毁、主备切换或金融级可用性认证。

新增普通确认任务的最小持久化机制，不替换既有生日联动工作流；恢复调度器只核对已提交交易的状态，**不会自动执行 waiting_confirmation 节点，不会重试转账、取消订阅等副作用工具**。

## 2. 健康检查契约

| 接口 | 成功 | 失败 | 判定依据 |
| --- | --- | --- | --- |
| `GET /healthz` | 200、`status=LIVE` | 进程或 HTTP 服务不可达 | 存活，不依赖数据库或调度器 |
| `GET /readyz` | 200、`status=READY` | 503、`status=NOT_READY` | 数据库实际可写、恢复调度线程存活且心跳新鲜、检查点存储未进入故障锁定 |

就绪响应中的 `checks`：

- `database_writable`：另开 SQLite 连接（只允许打开已有文件，100ms 锁等待），`BEGIN IMMEDIATE` 后执行实际 `INSERT`，然后回滚；不是只做 `SELECT 1`，不产生业务数据。
- `scheduler_running`：恢复调度线程存活、未停止、未异常退出，且最近一次核对循环结束距今小于 5 秒；默认每 250ms 核对一次。
- `checkpoint_available`：本进程未发生检查点写失败。失败后停止接受新的确认业务，直到排障重启；不因一次后续探测成功就自动解除。

数据库锁占用、写入错误、调度器停止/异常/心跳陈旧均会使就绪检查失败，但不影响 `/healthz` 的存活语义。探测响应不暴露数据库路径、异常堆栈、凭证或验证码。

兼容性：`/health/live` 继续可用；既有 `/health/ready` 仍是**配置预检**，不等同于新增的运行态 `/readyz`。部署接入运行态探针时应明确选择 `/readyz`，本任务未修改现有 Docker/Compose 配置。

## 3. 确认任务检查点与恢复规则

实现入口：`AgentRuntime`、`RecoveryMixin`、`RecoveryStore`、`RecoveryScheduler`、`durable_action`。

| 持久状态 | 恢复后的行为 |
| --- | --- |
| `waiting_confirmation` | 恢复原计划、确认有效期和认证凭证；等待用户继续确认，不能自动执行 |
| `processing` | 原确认凭据不能再次执行；只按原幂等键查核心，不重新调用副作用工具 |
| `succeeded / failed / reversed` | 不重新执行；转账状态查询再次核对核心，能识别成功后的冲正 |
| `recovery_required` | 未找到确定的核心结果或无法恢复非转账工具结果；提示人工核对，不声称成功或“未扣款”，不自动重试 |
| `cancelled / expired / deferred` | 不重新加入待确认队列 |

关键顺序：

1. `chat` 生成确认计划后，先提交检查点，再回复 `task_status=waiting_confirmation`。
2. 用户确认时仍经过原有 token、用户/设备绑定、PolicyEngine 和认证凭证校验；C8 不新增绕过策略的恢复执行入口。
3. **调用副作用工具之前**，提交 `processing` 检查点（包含一次性凭证的消费状态）。
4. 工具执行结束后保存最终任务状态；转账成败仍来自核心状态查询。
5. 若进程在第 3～4 步之间崩溃，恢复只查原交易。没有确定结果则进入人工核对，不猜测结果、不自动重试。
6. 检查点写失败返回 `RECOVERY_UNAVAILABLE`（HTTP 503），文案为“任务状态暂时无法确认，请勿重复操作，请联系人工核实”。即使核心已扣款而最终检查点写失败，也不谎称“未发生扣款”。

同一任务的确认/认证/取消使用任务级锁；不同任务保持并发，继续由原有核心原子风控检查防止跨越交易窗口。恢复调度器跳过正在办理的任务，不与正常执行竞争。

### 认证有效期与锁定

检查点包含完整认证绑定、原始到期时刻、认证是否通过、错误次数、锁定标记、失效原因和 `used_at`。重启不延长 5 分钟认证有效期，也不恢复“直接执行”的内存授权。

- 明确提交过期凭证：`AUTH_EXPIRED`，不执行。
- 重新请求确认：签发新挑战，必须重新认证后再确认。
- 已消费凭证：重启后仍拒绝重放并写 `auth.replay`。
- 错误验证码 3 次锁定：重启后仍然锁定，不因全局熔断器重新初始化而绕过任务锁。
- 确认卡片原有 10 分钟有效期不因恢复而延长；卡片也过期时必须重新发起需求。
- 对恢复的强认证待确认任务重新校验审计链；证据链仍异常时按 C5 规则冻结，不能利用重启绕过冻结。

### 恢复任务状态查询

`POST /api/v1/tasks/status`，JSON 请求字段：`task_id`、`action_token`、`user_id`、`device_id`。

使用 POST 是为了不把确认凭据放进 URL/访问日志。token 和用户/设备必须与持久计划一致，否则返回 403、`TASK_ACCESS_DENIED`；仅返回任务标识、trace、状态和安全文案，不返回 token、验证码、完整计划实体或认证 nonce。

`processing` 固定回复：**“银行还在确认这笔交易，请不要重复操作”**。恢复核对发现状态变化时写入 `task.recovery.reconciled`，记录来源、任务和交易状态；事件仍进入既有审计哈希链。

## 4. 一键故障演练

在仓库根目录执行：

```sh
python3 scripts/drill_recovery.py
```

输出 JSON：顶层 `status=PASS|FAIL`、逐项检查结果、RTO 实测和作用域；PASS 退出码 0，FAIL 退出码 1。可用 `--rto-target-seconds 30` 调整**演示目标**。失败报告不回显服务日志、操作 token、凭证 nonce 或验证码。

演练过程：

1. 创建独立临时目录/数据库，强制离线，启动独立服务子进程。服务自己绑定 `127.0.0.1:0` 获取空闲端口，不抢占现有演示端口。
2. 发起向妈妈转 100 元的任务，确认已持久化为 `waiting_confirmation`。
3. 对脚本自己创建的 PID 发送 SIGKILL；使用同一临时库重启。
4. 验证仍为 `waiting_confirmation`，跨多个调度周期没有自动转账。
5. 并发双击确认，只有一笔成功交易；查询最终状态，并核对数据库只有一次扣款。
6. 发起 5000 元强认证任务，认证通过但尚未最终确认时再 SIGKILL。
7. **仅在停机后的私有临时库中**将该认证挑战的 `expires_at` 改为过去，确定性模拟 5 分钟超时。不是修改系统时间，不提供 HTTP 故障注入端点。
8. 重启后验证旧凭证被拒，重新认证和确认才能完成；凭证重放被拒；两条审计链的 `valid` 必须为真。
9. 完成后第三次 SIGKILL/重启，再次验证已完成确认和已使用凭证不能重放。
10. 核对总共 2 笔交易、净扣款 510000 分、2 次 `consent.granted`。无论成功失败都回收自有子进程及临时库。

脚本不会查询或 kill 已有服务，不使用仓库现有演示数据库。服务启动使用的新配置项：

- `BANK_AGENT_DB_PATH`：数据库文件位置，未设置时沿用现有默认路径。
- `BANK_AGENT_OFFLINE=1`：强制离线意图解析，演练不调用外部 LLM。

## 5. RPO / RTO：仅演示级目标

| 指标 | 演示目标及计量方法 | 不涵盖的情况 |
| --- | --- | --- |
| RPO | **已成功应答的待确认任务状态零丢失**；脚本核对 2 个不同确认任务恢复后的状态、认证门禁及账务结果 | 未应答请求、磁盘损坏/丢失、断电持久化保证、跨节点复制丢失 |
| RTO | **每次不超过 30 秒**；从发出 kill 前的单调时钟时刻，到同库新进程 `/healthz` 与 `/readyz` 同时通过（包含进程回收、重启与第二次认证过期注入开销） | 人工发现故障的等待、人工业务核对时间、真实核心可用性和业务完全恢复时长 |

2026-09-21 本地独立演练样本：52 项检查 PASS，3 次恢复就绪分别为 0.116 / 0.112 / 0.117 秒，任务状态丢失 0，2 笔交易，无重复扣款；这是本机样本而非性能承诺。以每次脚本输出的 `rto_observed_seconds` 为准。

**“任务状态零丢失”在这里是有限场景的演示级验证，不宣称生产灾备验收或端到端 exactly-once。**

新增 `tests/test_c8_recovery.py` 的 **18 项测试**，覆盖：

- 待确认恢复不执行、完成后不重放、取消/过期不复活；
- 认证过期重认证、错误三次跨重启锁定、已用凭证重放；
- 核心提交前/后崩溃，不重试副作用，分别进入人工核对或查询到原交易；

- 数据库实际写锁、调度线程故障/停机/过期心跳、存活与就绪语义；
- 状态查询 token/user/device 绑定与输出最小化；
- 可显式开启的真实 SIGKILL + HTTP 集成演练。

## 7. 生产替换点 / 已知限制

- **任务状态库**：SQLite 单进程任务锁替换为受控工作流存储、持久队列和版本号/CAS；多副本租约、冲突处理、迁移及保留周期需独立验收。
- **核心交互**：`_row_for_idempotency` 的本地表定位 + `query_transaction` 替换为真实核心按业务流水号/幂等键查询接口。`recovery_required` 接入人工对账、补偿审批，不允许自动重新转账。
- **事务与审计**：当前检查点、认证/审计、核心提交不是一个跨系统原子事务；失败窗口通过“不重试、状态不明转人工”收敛。生产需要事务 Outbox、可证明的对账闭环及 WORM/SIEM，不得据此宣称所有副作用 exactly-once。
- **敏感状态**：临时库包含恢复必需的计划/认证状态及确认凭据，属于受限业务存储，不是日志或公开导出物；生产应采用服务端凭据摘要/密钥托管、字段加密、KMS、最小权限和数据留存策略。本实现不宣称本地数据库抗离线篡改。
- **身份**：查询接口的 user/device 是演示绑定上下文，不能替代银行登录身份与设备证明；生产需可信网关注入认证主体，不能信任客户端自报。
- **调度器与探针**：本轮常驻线程是“只读恢复状态核对器”，不是完整生产任务调度平台，也没有重写生日联动调度。生产接入监督器、存储主节点/核心连接健康检查、指标告警和故障接管；就绪不等于全部业务和合规已可上线。
- **其他 Mock 业务**：部分非转账业务状态仍是内存模拟，执行中断且无可查询凭证时转人工。本轮账务恢复验证针对持久化 MockBankCore 转账，不宣称所有模拟业务均获得完整灾备能力。
- **基础设施**：故障演练限 Unix 本地进程 SIGKILL；实际电源/存储故障、多实例并发、异地切换与生产 SLO 必须单独测试。
