# T14 离线发行包与验收

## 本批状态与适用边界

本批在现有 Dockerfile、Compose、T04/T07 和 T10–T12 源码基础上增加打包及验收入口，不改变银行功能、契约或权限。运行时仍为标准库。目标平台 **Linux/amd64**；Windows/macOS 使用预装 Docker 的 Linux 引擎。Docker 引擎、虚拟化及 Compose 不随包安装，不承诺所有系统/CPU 可运行。

## 维护者操作（引擎恢复后）

在项目根目录执行，需宿主 Python、Docker Linux/amd64 引擎，以及本地已存在、来源可信的 `python:3.12-slim`。本批打包器不会拉镜像；缺少基础镜像时停止，应先在联网的准备环境获取/校验，不能让接收方首次联网补环境。

```powershell
python scripts/offline_release.py build .qa-tools/releases/t14-linux-amd64
python scripts/offline_release.py verify .qa-tools/releases/t14-linux-amd64
python scripts/offline_qa.py .qa-tools/releases/t14-linux-amd64
python scripts/sandbox_qa.py
```

输出目录必须不存在，失败后保留不完整输出供诊断；不得把缺少 manifest 的目录发给他人。改用新的输出目录重试，不自动覆盖旧包。`.qa-tools/` 已被 Git 和普通 Docker 构建排除；本批生成包只是本地产物，不等于已上传到 GitHub。

## 包内内容

| 文件 | 用途 |
|---|---|
| images.tar | 同时保存最新应用镜像与沙箱基础镜像，包括其 Python 运行时和系统层 |
| compose.json | 无 build，pull_policy=never，本机 8090 端口、内部网络、独立命名数据卷、强制离线/关闭语音 |
| manifest.json | 平台、两个镜像 ID/标签、逐文件校验值及打包源码哈希 |
| SHA256SUMS | 含 manifest 的校验清单，检测传输损坏；不是发布者签名 |
| verify.ps1 / verify.sh | PowerShell 7（须允许本地脚本）、Linux/macOS 校验入口；Windows 禁用脚本时按 START_HERE 用 Get-FileHash 逐文件比较，不修改系统执行策略 |
| START_HERE.md | 接收方前置条件、导入、启动、保留数据、停止和演示边界 |
| offline_release.py | 可选的 Python 完整性核验器；Web 演示本身不要求宿主 Python |

打包采用白名单暂存：app/config/scripts/tests/eval 的受支持源码及固定根文件，不读取 `_internal/`，不包含 .env、历史 ZIP、日常数据库、浏览器测试工具或提交素材。拒绝符号链接。保留 eval 语料和 feature README，防止发行镜像缺失运行/测试资料；具体白名单见 `scripts/offline_release.py`。代码应以 manifest 对应快照为准，不能用 Git HEAD 代替尚未提交的源码。

应用网络为 internal；沙箱仍是独立、无网络/主机挂载的 T07 容器演示，不向银行容器挂 Docker socket。基础镜像标签导入可能改变接收方现有 `python:3.12-slim` 指向；接收方如有不同版本应先自行保留别名或使用独立引擎。QA 遇到同名异 ID 标签会停止，不静默覆盖。

## 接收方操作（实际包生成并验收后使用）

完整复制发行目录；先按 START_HERE 校验，再执行：

```sh
docker load --input images.tar
docker compose -p bank-agent-offline -f compose.json up -d --no-build --pull never
# 浏览器 http://127.0.0.1:8090
docker compose -p bank-agent-offline -f compose.json down
```

不要使用原项目的 `docker compose up --build` 代替离线启动。命名卷保留演示数据；同一 project name 会沿用原卷，换目录不会自动清空。新演示应选新项目名，保留数据应沿用旧项目名。不要随意 `down -v`。8090 端口冲突时先停自己的旧实例，或明确修改包配置并重新校验/记录，不能误停他人容器。

源码仓库与完整镜像归档分别交付。归档是否通过 GitHub Release 等分发、可见性、平台限制及上传授权在 T17 确认；本批不上传，不声称 Git 普通源码下载已包含全部环境。

## 验收范围

`scripts/offline_qa.py` 先核验完整性，再导入归档并核对镜像 ID，验证镜像内源码/空数据边界。测试使用随机项目名、临时配置和独立命名卷，端口随机绑定 127.0.0.1；最后只清理本次项目/卷，不接触日常数据。

检查包括：禁止构建/拉取、Docker 内部网络状态及出站连接失败、前端/健康/生产阻断、订阅确认、上下文补齐、固定 Supervisor、黄/红流程、防注入、本地工单领取/结单，以及重建后的余额、接管、审计和防重放。终端渠道单独以 `--network none --pull never` 运行。管理令牌只用于临时验收，不随包提供默认管理员密码。

记录保存至 `data/verification/t14-*/report.json`。T07 的真实沙箱专项另用现有 sandbox_qa 复验，宿主完整回归用 browser_qa --full。测试不会关闭宿主网卡、清空 Docker 缓存或模拟第二台物理电脑；镜像归档导入在同机缓存环境进行。最终仍需接收方在目标电脑实际断网复验，不能据此宣称跨机验收完成。
