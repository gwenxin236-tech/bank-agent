# 澜银行 AI 智能体技术文档

版本：2026-11-01；N16功能与交付材料同步版。默认离线Mock，可选本地Fineract、密码＋TOTP及云模型；不代表生产银行。

本文阐述澜银行AI智能体的业务目标、系统架构、领域协作、可信执行、安全机制与验证结果。当前可验证实现和未完成边界分别列示，正文上标引用对应附录中的源码、测试和材料位置。

## 1. 背景与问题分析

### 1.1 产品定位与业务问题

澜银行 AI 智能体把自然语言请求转换为可解释的银行业务计划。系统面向“说清想办什么，但不熟悉入口和步骤”的使用情形：查询账户、核对消费、向已核验收款人转账、治理订阅，以及家庭代办和生日延迟任务。它通过计划卡、确认、演示认证和逐项回执连接理解与执行，而不以流畅回答代替业务事实。[S01][S03][S06]

本项目所述问题来自现有场景设计与演示实现，不是独立用户调研结论；未提供外部样本量、行业渗透率或经济收益的实测证据。产品目标是降低操作理解成本，同时保持金额、身份、权限和执行结果可核对。默认规则模式保证不配置外部模型也能演示，模型能力与资金授权分离。[S16][S28]

### 1.2 核心技术难点

| 技术难点 | 本项目处理方法 | 必须保持的边界 |
|---|---|---|
| 模糊表达与缺失要素 | 有限转账草稿补齐，缺收款账户或金额先澄清 | 不把亲属称呼自动绑定为真实账户 |
| 语言建议与资金权限 | PolicyEngine 独立分色，执行前重校验 | 模型、领域建议和前端偏好不能授权 |
| 超时后的事实不确定性 | 区分成功、失败、处理中与未知，查询原幂等请求 | 不把超时当失败后自动再转一次 |
| 跨领域意见不一致 | 绑定平台快照，保留冲突及其来源 | 不用投票或最后覆盖决定事实 |
| 延迟任务与进程中断 | DAG 持久化、恢复与声明式补偿 | 已受理交易不能任意强杀或伪造退款 |
| 可操作性与可验证性 | 清晰确认、适老显示、审计回放和本地接管 | 自动化检查不等于真实读屏或生产认证 |

上述机制分别落在原运行时、多域协调、任务图与前端，不另建一套脱离权限链的 Agent 执行器。[S03][S10][S11][S15][S23]

### 1.3 要求分层与实施范围

L1 为赛题“三、核心技术要求”，包括权限、防幻觉、防注入、审计、熔断、受限可监控隔离、意图与上下文、DAG、中断、回退及人工接管。L2 为“五、作品资料”，包括架构、算法、安全设计、简介、PPT、视频、源码及部署测试、安全自评。本文覆盖技术文档所需架构、算法与安全设计，并给出实现证据。[S01][S27]

六领域Agent、RAG、OCR、音频摘要、自由规划扩展和完整离线发行属于项目自定目标，不增列为官方硬性条文。P03已提供本地向量与独立重排，P04提供本地OCR；微调和本地聊天大模型未列入已实现。自建Web用户/坐席和本地密码＋TOTP已接入，可选Fineract只办理虚构资金；第三方官方IM、持牌银行和生产认证仍未接入。[S27][S30][S50][S53][S58][S59]

### 1.4 从自然语言入口到可执行银行任务

#### 1.4.1 用户意图与银行动作之间的差距

- **自然语言到银行要素的映射：**

  “给妈妈转200元”在语言层面包含收款人称呼和金额，在银行层面还缺少账户核验、付款账户状态、当日累计额度、操作身份、设备与本次确认。项目把这些差距显式转成预检维度和计划步骤。这样，用户看到的不是模型直接作出的“已经转好”，而是可核对目标、金额和办理门槛的计划；只有工具证实终态后才能给出成功回执。[S03][S04][S31]

- **显示意图与业务动作分离：**

  “不显示这张卡”则有完全不同的业务语义：它只描述显示偏好，不应被含有“卡”的通用意图误归为卡片管理，更不能因同句出现“不要挂失”就执行挂失。当前解析器先识别这类显示请求，返回设置指引，核心卡片状态保持不变。这体现了本项目对否定表达和副作用隔离的工程处理，而不是靠回复措辞掩盖错误执行。[S20][S23][S26]

#### 1.4.2 场景、交互及验收条件

- **场景输入与结束条件：**

| 场景输入 | 系统必须给出的中间证据 | 结束条件 |
|---|---|---|
| 我要转账，再补给妈妈、200元 | 同会话草稿补齐后的新计划、核验目录和权限要求 | 重新确认前余额不变 |
| 给妈妈转5000元 | 红色计划、绑定本次操作的认证请求 | 认证后仍须再次确认 |
| 查一下我的全部资产 | 账户来源清单、覆盖范围和不完整声明 | 不能把单账户金额说成家庭总资产 |
| 取消某视频订阅 | 精确订阅对象、扣费授权与服务/退款层状态 | 未知退款不宣称已到账 |
| 为爱人安排生日礼物 | 明确生日、分别绑定的鲜花/蛋糕日期、预算锁 | 延迟节点到期只执行一次 |
| 不显示这张卡 | 本页显示设置及恢复路径 | 不改变卡状态、不触发强认证写操作 |
| 原工单已结单后再次求助 | 新请求标识、新工单、与旧工单的状态隔离 | 丢回复重试仍只有一个新工单 |

- **验收条件的依据：**

  以上条件来自当前主链和测试场景，不是新增尚未实现的需求；完整边界仍以第8章和证据索引为准。[S25][S26]

## 2. 整体技术方案

### 2.1 系统架构总体概览

默认应用采用Python标准库服务和浏览器前端，可选本地RAG/重排/OCR使用单独固定校验的依赖和模型。Web请求经演示身份或自建密码＋TOTP会话检查进入AgentRuntime；本地终端通过统一网关适配，自建坐席使用原工单与角色边界。运行时执行输入安全检查、规则或受限模型解析、权限判定、原计划生成和多域证据核对；获得必要确认及认证后，才进入持久 DAG 与固定工具。MockBankCore或固定本地Fineract提供虚构账户事实，SQLite保存平台任务/审计/会话；AuditStore记录关键链路。[S03][S08][S10][S15][S18][S28]

### 2.2 技术路线与关键约束

| 阶段 | 输入与处理 | 输出及约束 |
|---|---|---|
| 接入 | 可信演示会话、设备、渠道与请求标识 | 绑定身份；请求体自报身份不能提权 |
| 理解 | 注入检查、规则解析、有限上下文、可选模型受限 JSON | 意图与业务实体；金额保持整数分 |
| 核对 | 平台预检、领域快照与 Supervisor 来源比对 | 原计划核对结果，不生成授权 |
| 授权 | 原确认 token、摘要绑定、红色认证和再次确认 | 当前操作的一次性执行许可 |
| 执行 | DAG、固定工具、执行前权限和核心状态复核 | ToolResult、幂等指令及最终状态 |
| 反馈 | 事实归一化、逐项回执、审计与接管 | 不把未知说成成功，不自动重试副作用 |

默认运行依赖保持标准库；本地RAG/重排/OCR为已批准的可选依赖和模型，随对应离线镜像交付；浏览器测试和PDF/PPT制作工具属于开发环境。金额不能使用浮点数表示，模型输出只是待检请求，工具结果才是账户和交易回复的事实来源。[S02][S06][S13][S28]

### 2.3 工程亮点与可核对效果

本项目的工程贡献在于约束和连接既有业务链：将领域建议限制为只读快照分析，将三色权限留在平台，将任务过程持久化，并在未知结果、失败恢复和本地接管时保持账务语义一致。六域齐全不意味着每次调用六域，也不意味着六个自主联网大模型。[S13][S14][S15]

本轮最终完整源码回归为888项通过、0跳过、0资源警告，日常数据库指纹未变化。该结果是指定 Mock 快照的自动化证据，不是业务成功率、真实用户满意度、P95时延或生产可用率；本文不把测试数量换算成功能完成百分比。[S25]

### 2.4 模块职责、接口与调用边界

#### 2.4.1 理解核对层与安全执行层

- **理解核对与资金执行分工：**

  理解核对层输出意图、实体、Finding、Proposal及Coordination；安全执行层处理正式计划、确认凭据、PolicyEngine、工具分派和核心状态。两层通过经过检查的数据交接，而不共享可被领域 Agent 随意调用的银行句柄。支付 Agent 的构造参数是 PaymentSnapshot，不是 Bank、Runtime、DB 或任意回调；其纯分析测试验证不写核心、不发通知、不直接写审计。[S13][S35][S36]

- **规划异常与执行后异常分开处理：**

  运行时负责把分析结果接回原链。规划期间分析或来源核对异常会阻止本次计划进入待执行队列；工具已返回之后的后置分析异常只记录 unavailable，不重复查账或重新发起副作用。两类故障位置不同，因此不能用一个“Agent异常后重试整个流程”处理。[S15][S49]

#### 2.4.2 核心组件的输入、输出与调用方

- **组件接口与职责边界：**

| 组件 | 输入和主要输出 | 谁能继续推进 |
|---|---|---|
| IntentParser | 用户文本到受限意图/实体 | Planner 仍须生成正式计划 |
| PolicyEngine | 当前实体、账户/风险事实到权限与暂缓原因 | 仅原Runtime确认/执行入口 |
| PreflightReport | 六项只读检查到三态和证据 | 预检自身不能授权或扣款 |
| DomainAgent | 绑定Context的快照到事实和候选步骤 | Supervisor核对，不直接执行 |
| Supervisor | 固定路由、来源与参数核对到Coordination | 原计划模板及原确认入口 |
| DagExecutor | 通过既有授权的节点到工具结果和状态转移 | 注入的原工具分派器 |
| MockBankCore | 幂等指令、状态查询到模拟核心事实 | 原策略复核与核心锁内操作 |
| AuditStore | 关键事件到哈希链和回放记录 | 只记录证据，不补发业务 |

#### 2.4.3 请求内数据的生命周期

- **请求标识与身份数据贯通：**

  一次请求的trace贯穿输入、安全检查、计划、领域核对、确认、认证、工具与结果。session仅用于隔离草稿，不代表身份；actor/device由可信演示会话确定，subject可以是被授权代办的账户主体。请求文本进入解析器，银行事实进入工具结果或快照，认证凭据进入独立凭证簿，三种数据不应相互冒充。[S04][S13][S21]

- **计划绑定与最小化持久状态：**

  同一计划可在后续确认请求中继续，但其实体和摘要不能被悄悄替换。重新输入不同金额、收款人或设备时，系统必须重新规划或重新认证。DAG只保存完成恢复所需的状态，审计保存必要的脱敏决策证据，浏览器显示偏好只存卡片ID。[S04][S12][S23][S38]

## 3. 数据、实体与上下文设计

### 3.1 事实来源与数据分类

| 数据类型 | 当前来源 | 使用限制 |
|---|---|---|
| 请求实体 | 规则解析或通过校验的可选模型输出 | 是用户请求，不能当已成交事实 |
| 账户与交易 | MockBankCore、核心状态/幂等查询 | 仅模拟银行，不是银行受理凭据 |
| 权限与阈值 | config/policy.json、PolicyEngine | 由服务端计算，不能被 Prompt 覆盖 |
| 预检与预算 | 平台已有查询和派生计算 | 引用原证据，不另造完整资产总额 |
| 领域分析 | 绑定上下文的不可变快照 | 建议无执行权限，未知不补零 |
| 过程与恢复 | DAG/审计 SQLite 记录 | 不替代真实核心最终账务或 WORM |

余额工具同时给出来源清单和 complete=false，范围为当前授权的模拟活期可用余额。回复明确未覆盖其他银行、未导入账户、理财及锁定资金，因此“全部资产”查询不会被单账户金额冒充；来源异常不会报告余额读取成功。[S06][S20][S26]

### 3.2 DomainContext 与不可变契约

DomainContext 关联 trace、session、actor、subject、device、channel、用户文本及实体。actor 表示操作发起者，subject 表示账户主体，家庭代办不能将两者混为同一身份。Finding 包含来源化事实、缺失项、风险信号与建议；Proposal 只表达候选步骤和用户选项。[S13][S21]

契约把字典/列表递归冻结，序列化返回独立副本；拒绝浮点数、非 JSON 对象以及授权或凭据字段。*_cents 只能是整数，bool 和数字字符串不能伪装金额。结构深度、条目和字符串长度受限，未知顶层字段不能静默进入执行协议。[S13]

信封绑定发送域、接收者及同一上下文摘要。引用字符串本身不证明事实真实，Supervisor 还需与本次可信平台快照比对。当前 Python 模块是受信代码协作边界，不是不可信插件隔离或银行数字签名证明。[S14][S15]

### 3.3 有限转账上下文

转账草稿只保存缺失收款人和整数分金额所需的小量字段，按身份、设备、渠道和会话隔离，最长5分钟、最多3条补齐轮次。它不保存聊天全文、余额、备注、账号、口令、验证码或确认凭据。家庭代理和受管理账户暂不启用该草稿记忆，避免跨授权关系继承。[S16]

例如用户先说“我要转账”，再补“给妈妈”“200元”，平台会重新解析并展示新计划，补齐本身不扣款。换设备、换身份、超时或超轮数不继承旧草稿；显式账号和未核验收款人继续要求核对，不自动猜测绑定。[S16][S26]

### 3.4 演示数据与隐私边界

离线默认不调用外部模型。可选模型仅发送用户文本、不附账户查询结果，但尚无完整外发 PII 脱敏证明；可选语音经本次显式同意后将音频发送至配置的外部 ASR。二者只使用虚构演示输入，不能据此沿用真实客户文本和录音。[S22][S24]

审计使用必要字段和脱敏摘要，不等于所有材料、二进制或历史均已完成隐私审核。真实供应商协议、留存政策、区域隔离、字段加密与生产 KMS 等仍须独立审查；本地发布检查也不代表已有外部发布授权。[S29]

### 3.5 结构化数据协议与来源追踪

#### 3.5.1 只读预检的数据结构

- **预检字段与三态输出：**

  每项预检包含key、label、status、message和evidence。**status固定为satisfied、missing、unknown**；前两者描述已知事实是否满足，第三者表示缺少可信输入。接口把缺失维度和未知维度分开展示，避免把“查不到”简单编码成false，更避免给余额补零后计算出确定结论。[S31]

:::code S31 -1 13

- **未知事实与已知不足分别处理：**

  例如余额查询异常时，可用资金维度为unknown，evidence仅保留本次请求金额等可确认内容；当可信余额确实低于金额时才是missing。付款卡列表为空同样属于unknown，不能因为没有发现异常卡就判为正常。模型和领域模块收到的是这个已分类的报告，不再重写数据获取逻辑。[S31]

#### 3.5.2 Context摘要绑定与快照复用拒绝

- **上下文摘要与快照绑定：**

  context_digest以整个DomainContext的规范化序列化内容计算**SHA256**，参与字段包括trace、session、actor、subject、device、channel、输入与实体。PaymentSnapshot先验证预检主体等于subject、金额和收款人等于本次实体，再记录context_key。相同金额的两笔不同会话交易也不能复用同一快照。[S35]

:::code S35 0 5

- **摘要的信任边界：**

  这里的摘要解决的是本地受信组件间的数据绑定：原字典后续变化不会污染冻结快照，换身份或换输入会得到不同摘要。它不提供银行签名或远程证明；如果平台将未授权HTTP字典误包装成可信快照，仅靠摘要不能把假事实变真。当前实现因此限定快照的来源构造路径，并在Supervisor中检查类型、来源集合和具体内容。[S13][S15][S35]

#### 3.5.3 核心、任务和审计存储的角色

- **核心记录与关键字段：**

| 表或记录 | 关键字段 | 用途与一致性要求 |
|---|---|---|
| core_transactions | transaction_id、唯一idempotency_key、status、amount_cents、actor_id、debit_applied、状态历史 | 保存模拟核心受理和扣账事实；查询原请求支持不重复扣款 |
| task_dags | dag_id、trace_id、actor_id、status、state_json、更新时间 | 保存依赖图、节点结果和恢复元数据 |
| audit_events | 全局seq、prev_hash、current_hash、trace/任务/身份、脱敏payload | 记录关键决策与状态，按trace回放并验证链关联 |
| local_handoff_cases | case_id、唯一source_key、用户设备、坐席设备、状态与固定结论 | 工单和审计同事务，不代替账务结算 |
| 凭证簿 | credential_id、AuthBinding、摘要、时效、nonce、passed、used_at | 单机演示内存凭据；消费一次后拒绝重放 |

- **存储职责与恢复证据隔离：**

  核心事实、工作流状态、日志和凭据分工不同。重建进程时有成功核心证据的节点不再调用工具，内存凭证过期或消失也不能凭持久图绕过认证。把所有状态合并成一张“聊天记忆表”会失去这些语义区别，本项目继续复用原模块职责。[S08][S12][S19][S38]

### 3.6 双口径账本与资金状态

#### 3.6.1 消费、现金流和资金状态分别计算

- **消费、现金流和资金状态分工：**

  消费视图回答“实际花了多少”，现金流视图回答“该账户流出了多少”，资金状态回答“当前哪些资金能用”。信用卡还款和本人账户间转账会导致现金流出，但不应再次算为消费；退款降低对应消费口径，预计到账不增加当前可用资金。[S34][S45]

:::figure ledger
图3-1 双口径账本、资金状态与明确来源关联

- **状态筛选与入账日期归属：**

  账本首先根据状态分离processing、restricted、expected和completed记录，再按视图筛选已完成候选。消费以实际消费和已核实退款计算，现金流按已入账正负金额求和；无法确定已完成的记录单列，不进入已完成总额。日期优先使用posted_date，其次settled_date/date，避免跨月退款被放回错误月份。[S34]

#### 3.6.2 去重和退款的计算规则

- **明确关联去重：**

  去重仅接受canonical_id、original_transaction_id或linked_transaction_id等**明确跨源关联**；商户、金额和日期相同不足以认定重复。否则两次真实同额购买会被误删，也可能将还款与原消费错误合并。缺少明确关联时保留记录并维持来源范围，而不是由模型猜测。[S34]

:::code S34 0 10

- **退款归属与覆盖范围说明：**

  在当前周期，净消费按“已完成消费金额减已核实退款”计算并在零处截断；没有本周期消费的退款仍单列金额，不能让当期消费变成负值。现金流净流出为已入账流出减流入，允许与消费总额不同。覆盖范围由工具给出的coverage解释，不能把一个账户的双口径结果称作家庭完整资产。[S34][S45]

## 4. 核心算法与多领域协作

### 4.1 意图解析与缺失信息处理

本地规则优先处理资金与安全敏感意图，金额转为整数分，收款人须进入已有核验流程。可选模型输出只能进入受限意图/实体协议，不能决定风险颜色、跳过确认或指定任意工具。缺金额、目标或安全账户信息时返回澄清，而不是填入一个看似合理的默认值。[S03][S22][S26]

生日日期采用有限规则：显式年份保留，缺失或非法日期要求补充；鲜花和蛋糕可分别指定0至365个整数提前天数，默认分别为2天和1天。无效、矛盾、无法明确对应对象或已过订购日的安排拒绝创建。两个天数进入计划详情与原摘要绑定，确认后形成原 DAG 延迟节点，不将全部任务统一为提前两天。[S20][S26]

### 4.2 三色权限与执行前复核

| 级别 | 当前演示规则与示例 | 实际办理门槛 |
|---|---|---|
| 绿色 | 策略允许的余额、流水、账单、理财收益等查询 | 安全与归属检查后执行 |
| 黄色 | 日累计不超过1000元的转账、订阅查询及取消订阅 | 展示原计划，用户明确确认 |
| 红色 | 日累计超过1000元的转账、卡片管理等 | 演示强验证通过后再次确认 |

金额阈值只是基础分级，风险、授权、余额、额度、设备或账户状态仍可升级或阻止请求。订阅查询虽只读，仍保留赛题黄色确认口径。配置中的业务名称不代表所有真实银行业务已经对接；密码等实际办理仍可能转官方人工。[S01][S02][S03]

```text
读取原计划与 token
核对身份、设备、计划摘要及有效期
重新计算当前策略和资金/预算约束
若不允许或必要事实未知：停止或返回核对选项
若要求强验证：核验绑定当前计划的一次性凭据
消费凭据并通过原执行器调用固定工具
读取工具/核心状态，持久化事实与审计
```

认证成功不会直接扣款：用户仍须携带原计划及认证凭据再次确认。改金额、收款人或绑定上下文会使旧凭据失效；认证、确认、核心幂等共同约束重复提交，但不授权自动重试资金写操作。[S04][S05][S26]

#### 4.2.1 基础分色、风险升级与保护性暂缓

- **基础权限与保护性升级：**

  分色分两步：_base_classify先依据意图和当前日累计形成基础要求，classify再叠加可信风险特征、反洗钱拆分模式和家庭授权。其结果不仅有risk_level，还包含requires_confirmation、requires_strong_auth、defer、authz_allowed和decision_reason等信息。界面不能仅凭“红色”三个字推断仍允许输入验证码继续：保护性暂缓也可显示红色，但此时不会创建可执行转账。[S03]

- **风险特征与当前计分规则：**

  当前风险计分为确定性规则。新收款人加30分，金额达到100000分加20分，命中本地诈骗话术加50分，可信档案标记老年用户加20分，30分钟窗口内第3笔及以后转账加30分。合计达到60分触发暂缓；这些阈值由配置和服务端历史读取，不接受客户端自报risk_score、is_elderly或最近次数。[S02][S33]

:::code S33 0 22

- **风险分值的解释边界：**

  风险分是解释性特征，不是诈骗概率。1000元、亲属称呼或老年身份单独都不能证明诈骗。当前历史读取succeeded和processing记录，防止尚未终结的已受理转账被漏出风险窗口；未来时间记录不计入。若金额处于900元至不足1000元区间，同日达到第3笔时另产生疑似拆分标记，由策略升级强认证，而不是由反诈Agent自行封禁。[S03][S33][S44]

- **实现步骤：先计算基础权限，再读取可信风险因素，最后在原策略链内决定升级、暂缓或拒绝。**

#### 4.2.2 预检、认证与执行前复核的区别

- **预检、认证与执行复核分工：**

  预检为计划卡提供当时事实，认证表明用户通过本次验证，执行前复核检查事实是否仍然成立。三者缺一不可：用户在预检后可能修改金额，另一个请求可能消耗余额或额度，卡片也可能变为挂失。系统在核心锁和原确认入口再次核对，避免只凭旧报告执行。[S03][S04][S31]

- **认证条件缺失的处理：**

  需要确认的authentication维度在预检时为missing，这是正常的“尚**待用户完成条件**”，不应让支付Agent因这一维度未满足就永远不出计划。支付建议将认证要求原样带出，由原确认/强验证流程补齐；其他必要资金和对象事实未知则不产生写步骤。[S31][S36]

#### 4.2.3 红色认证时序与凭据状态

:::figure authentication
图4-1 红色转账的原计划确认、凭据核验与再次确认时序

- **认证绑定字段与有效期：**

  AuthBinding绑定user_id、device_id、task_id、node_id、operation_type、amount_cents和recipient；凭据另存operation_digest、创建/过期时间、nonce、尝试次数、passed和used_at。默认强认证有效期为300秒，确认token有效期配置为600秒，二者不是同一个凭据。[S02][S38]

:::code S38 0 17

- **凭据状态与单次消费：**

  凭证检查按失效原因、锁定、已使用、到期和绑定变化等情况拒绝；绑定变化即使改回原值也不能复活旧凭据。verify仅把绑定凭据标记为通过，confirm在执行前消费它。直接调用执行入口、跨用户凭据、换设备、重复确认及认证过期，都有专项用例证明不会绕过原门槛。[S04][S05][S38]

### 4.3 六领域划分与按需路由

| 领域 | 主要职责 | 当前事实来源 |
|---|---|---|
| payment | 支付预检、缺失约束与原转账步骤建议 | 已有 PreflightReport |
| antifraud | 已有风险因素与保护性提示 | 平台风险快照 |
| finance_health | 预算、账本和财务覆盖范围解释 | 已授权账本或同次预检预算投影 |
| family | actor/subject 关系与授权有效性解释 | 已有守护授权记录 |
| subscription | 订阅候选、服务/扣费/退款状态分析 | 确认后既有订阅工具结果 |
| card | 卡片状态、已知操作与必要核验建议 | 原卡管工具及状态证据 |

注册器只导入六个固定本地模块，先在临时表完成校验，再发布只读映射；缺域、重复、越域或异常导入不污染原注册表。注册不授予银行工具权限，实例不缓存跨客户事实。[S14]

转账规划按 payment、antifraud、finance_health 路由；家庭代办增加 family。订阅、卡片等按原授权工具返回后进行所属域分析，不为了多域协作提前读取黄色订阅或重做已经完成的工具。[S15]

### 4.4 来源核对、冲突保留与受控计划

Supervisor 检查域集合、上下文摘要、信封发送者、事实与证据、候选工具及参数。金额、收款人、订阅或卡片 ID 必须对应当前快照与实体；建议不能添加 retry、认证旁路或额外工具。旧全局演示来源不能贴成其他主体的银行资料。[S13][S15]

同一字段出现不同值时，保留各来源的 claims，不用多数投票、最后覆盖或未知补零。当前状态包括 ready、needs_review、needs_user_choice、needs_clarification；ready 仅代表资料可核对，不能转换为 authorized。[S15]

当前主动计划核对只接受原转账模板 resolve_beneficiary、check_transfer_constraints、create_transfer。预算缺口沿用调整金额、调整预算、延后或人工选项，不静默降额、不建议借款、不直接执行领域建议。重启恢复的 coordination 元数据也不能代替新鲜授权。[S15]

### 4.5 支付领域的六维预检与预算算法

#### 4.5.1 六项维度如何生成

:::figure preflight
图4-2 支付六维预检及三态证据输出

- **只读维度与证据来源：**

  预检依次读取余额、当日累计、可信收款目录、卡片状态和已确认未来支出，并接收平台已经计算出的认证要求。它刻意不调用会滚动核心日累计等内部状态的执行前约束方法，确保预检仍为**只读**。下游看到每一维的status、message、evidence和报告生成时间，而不是一个笼统“可转账”的布尔值。[S31][S32]

- **限额、卡状态与收款人判定：**

  日累计采用projected=current+amount，等于限额可满足，超过限额才记missing。卡状态存在受限卡时记missing，全为已知正常状态才满足；有未识别状态或空列表则unknown。收款目录匹配仅表示演示目录中存在，仍由原执行步骤核验；显式提供未核验账户时不因名称相同而沿用旧账户。[S31]

#### 4.5.2 预算约束公式与可追溯算例

- **预算变量与整数分公式：**

  设A为当前可用余额，C为已确认支出总和，B为安全缓冲，T为本次转账金额，**单位均为整数分**。实现计算：D=A-C-B；P=D-T；G=max(0,-P)。P非负表示当前已知预算满足，P为负时缺口为G。projected_income只保留为说明字段，不参与D、P和G的计算。[S32]

:::code S32 0 16

- **可追溯的预算缺口示例：**

  例如说明性算例A=1000000、C=600000、B=100000、T=400000，则D=300000、P=-100000、G=100000，即本次会产生1000元预算缺口。该算例用于解释代码公式，并非当前客户余额或本轮实测结果。平台应展示缺口并让用户选择调整金额、调整预算、延后或人工；不会把预计工资补入可用余额，也不会静默将4000元降成3000元执行。[S32][S36]

- **确认时重新读取约束：**

  预检后的预算可能变化，confirm会重新读取预算并保留原四种选项。只对第一次预检写测试而不覆盖确认前变化，无法证明实际执行安全；现有主链测试因此同时检查计划阶段与确认阶段的缺口处理。[S04][S49]

#### 4.5.3 PaymentAgent如何从事实形成建议

- **事实核对与建议分支优先级：**

  TransactionAgent先验证本次Finding等于同一快照重新计算的结果，避免调用方替换分析结果。预算已知缺口优先生成四种选择；对象或金额缺失时生成明确追问；其他非认证维度不满足时给重新核对/人工选项；仅必要事实齐全时建议原转账三步。它不重新发余额查询，也不拥有运行时或数据库句柄。[S35][S36]

:::code S36 0 24

- **建议标签与执行授权分离：**

  这段逻辑体现“分析存在”和“获得执行授权”之间的区别：建议中可以注明需要strong_auth，但即使建议漏掉或试图降级，原PolicyEngine和confirm仍独立要求红色认证；相反，建议里写了“可执行”也不能改变策略拒绝。[S03][S04][S36]

### 4.6 其他五个领域Agent的实现机制

#### 4.6.1 AntifraudAgent：解释已有风险，不重算权限

- **已有风险信号的解释输出：**

  反诈Agent从快照读取risk_factors中的code，以及平台已有signals和aml_suspect。它把这些信息写入Finding风险信号，用于向用户解释为何需要核实；有风险信号时只给review_risk_factors和human_handoff选项，suggested_steps为空。冷静期、冻结、通知守护人和转账暂缓仍由原平台处理。[S44]

- **避免重复计分与未知补全：**

  这一设计避免同一风险因素在策略和Agent之间被计算两次，也避免模型把“新收款人”描述成已经证实的诈骗。风险快照失败时SnapshotAgent添加verified_antifraud_facts等缺失信息，不能把空结果解释为“风险为零”。验证覆盖无授权字段、缺来源、伪造事实和不调用核心的纯分析路径。[S14][S44][S49]

#### 4.6.2 FinanceHealthAgent：区分账本口径与资产范围

- **双口径账本与来源覆盖：**

  财务Agent读取consumer、cash_flow、funds和coverage。coverage.complete不是true时增加coverage_incomplete信号；建议只包括review_budget和human_handoff，不建议自动借款、投资申购或通过预计收入弥补缺口。转账规划中的预算事实来自同次预检投影，不为了凑出完整财务报告额外读取账本。[S15][S34][S45]

- **确定性计算与异常路径验证：**

  消费、现金流出和可用资金来自不同确定性口径，因此Agent职责是解释，而不是让大模型加总。测试验证还款不重复算消费、退款分列、处理中金额不进入已完成总额，以及部分账户来源不能伪装成家庭资产全貌。[S34][S45]

#### 4.6.3 FamilyAgent：发起人、账户主体与授权记录

- **家庭授权缺失与失效反馈：**

  当actor不等于subject而缺少grant时，家庭Agent报告grant_id缺失；快照中授权已失效时报告grant_inactive；候选认证要求包含owner_verification，并给核对授权或人工选项。它不因为“妈妈”“女儿”这样的关系词推断操作权，也不能自行扩大额度或改变授权类型。[S42][S46]

- **平台授权复核与人工边界：**

  平台权限矩阵再检查guardian与subject是否匹配、授权是否生效/过期/撤销、delegate或assist模式、业务白名单、金额上限和当天额度。密码、挂失、解挂等本人业务不能因为full授权变成守护人可代办；assist模式仅协助发起，由本人认证并提交。授权额度在核心副作用前预占，失败可释放，未知结果不立刻释放，避免通过重试绕过额度。[S21][S42]

:::code S42 0 19

#### 4.6.4 SubscriptionAgent：交易、扣费授权、服务和退款

- **订阅对象和三层状态规范化：**

  订阅快照把历史扣款、未来扣费权限、是否可终止、服务有效期和退款状态分别规范化。未选subscription_id或选定对象不在快照内时，Finding报告缺对象，Proposal只列来自本次快照的候选；候选标签也须在Supervisor核对时与真实快照商户名称一致。[S15][S47]

- **取消授权与退款结论的区别：**

  仅当操作为cancel、对象已明确、terminable为true且debit_state为active时，Agent才建议cancel_subscription。建议仍标注明确确认，查询与取消都按黄色处理。refund_state为unknown时只能说待核验，停止未来扣费既不是终止服务，也不是历史费用已退回。[S02][S47]

#### 4.6.5 CardAgent：状态驱动的挂失/解挂建议

- **卡状态驱动的固定建议：**

  卡片Agent首先检查card_id是否存在于本次快照，并将未识别卡状态标成card_status_unknown。正常卡且操作为report_loss，或者已挂失卡且操作为unreport_loss，才建议读取卡状态、执行指定写操作、再次核验三步；已挂失卡不会再建议同一次挂失，操作/卡ID/状态不明则给澄清和人工选项。[S48]

- **卡片显示偏好不改变办理权限：**

  每个建议固定携带当前card_id，strong_auth只是平台所需条件的提示。前端“仅隐藏”不会进入该卡管建议链，也不会用隐藏偏好过滤付款卡预检。测试分别验证卡状态真正改变的Mock写操作，以及只变浏览器显示、核心状态和余额不变的展示操作。[S23][S26][S48]

## 5. 任务 DAG、事务与故障恢复

### 5.1 任务图与状态模型

TaskDag 保存节点、依赖、身份、状态及元数据，建图拓扑排序拒绝环。普通计划转成有依赖边的执行图，生日任务复用 action、delay、human_gate 节点；当前单线程调度，不承诺并行或任意 Agent 动态生成图。[S10][S11][S12]

:::figure birthday
图5-1 生日联动的依赖与已声明补偿

锁预算节点确认后执行，两个订购节点按各自天数分别到期。取消时只补偿已声明且可核对的预算锁，不声称商户已受理订单可以任意撤销。旧生日任务迁移保留原日期语义，已由 DAG 收养的任务不交回旧调度器双重执行。[S10][S20]

| 对象 | 状态与处理原则 |
|---|---|
| 节点 | pending、ready、running、succeeded、failed，另有 skipped、compensated |
| 任务 | running、paused、waiting_human、handoff、failed、completed，以及取消补偿状态 |
| 暂停 | 在节点安全边界停止推进，已受理调用不强杀 |
| 取消 | 停止未执行步骤，仅逆序执行已声明补偿 |
| 未知结果 | 保留待核验证据，不按普通失败自动补偿或重发 |

### 5.2 核心事务、幂等与逐项回执

每个任务节点有稳定幂等键，转账执行前再次核验资金、卡状态和额度。进程内核心锁约束本地并发，避免两个请求共同穿透演示限额；这不是分布式多进程额度控制。执行失败和核心结果未知是不同情形，未知时只查询原请求。[S03][S11][S26]

用户视图区分成功、处理中、结果未知、失败、部分完成及已补偿。成功交易的数值和标识来自工具；部分任务的已完成节点不会被一个“整体失败”抹掉。订阅停止扣费、服务有效期及退款状态分别展示，未来少扣的钱不增加当前现金。[S06][S26]

### 5.3 持久化与恢复策略

TaskDagStore 将图快照与关键状态事件写入既有 SQLite 审计存储。成功节点重启后从证据恢复，不再次调用工具；运行中的交易查询原核心状态；普通计划剩余动作需要新确认，强验证失效则重新认证。落盘异常停止推进，不以恢复名义重复扣款。[S11][S12][S26]

恢复测试包含进程中断、扣款后 checkpoint 故障、授权过期、暂停、迁移与重复恢复。证据仅限单机 Mock 条件，不包含磁盘毁损、跨地域切换、生产灾备或银行监管验收；真实 Adapter 必须提供持久幂等和只读状态核查。[S26][S29]

### 5.4 人工接管与新一轮求助

本地工单状态为 LOCAL_QUEUED、LOCAL_CLAIMED、LOCAL_CLOSED。用户只能查询本人同设备工单；本地坐席使用受信管理身份领取和记录固定结论。状态更新与审计同事务，身份变更、非法转移和审计失败不应留下假结单。[S19]

未知银行结果只允许记录仍需核对，LOCAL_CLOSED 不等于资金成功、已退款或接通真人。查询确认旧工单结单后，用户可主动发起新一轮；新请求使用新标识，丢失响应、原请求重试及正常存储条件下刷新不会重复建单。新一轮不修改旧工单，不恢复原交易。[S19][S23][S26]

### 5.5 DAG调度器的实现步骤

#### 5.5.1 图合法性与稳定拓扑排序

- **建图检查与稳定拓扑排序：**

  TaskDag初始化时检查节点非空、ID唯一、依赖存在、边不重复、状态合法及金额类型，然后调用稳定Kahn排序。算法建立node_id到节点的映射、每个节点的剩余入度和followers表；按原节点顺序收集零入度节点，逐个输出并降低后继入度。最后输出数量小于节点数时说明存在环，整个图在执行前拒绝。[S10][S40]

:::code S40 0 27

- **线性复杂度与环检测范围：**

  时间和空间随节点与依赖边线性增长，表达为O(V+E)。稳定性表示具有相同拓扑条件时保留确定的输入次序，不表示并发执行。即使一个环位于与主分支不连通的组件，也会因总输出数量不匹配而被检出；重复ID和未知依赖不等到运行时才暴露。[S40]

#### 5.5.2 节点分派与checkpoint边界

- **节点转移与落盘检查点：**

  DagExecutor用ready/running/succeeded等显式转移约束分派。on_change在状态变化和工具调用前同步保存快照与事件，失败时该执行器进入不可继续推进的状态；恢复必须重新从持久状态加载。工具通过注入的固定分派函数调用，DAG模块自身不导入银行Runtime、不授予权限、不执行动态表达式，也不自动重试。[S11][S41]

- **固定节点分派与人工审批边界：**

  action节点调用原工具，delay节点比较带时区的到期时间，human_gate等待显式决策。用户“批准”只能作用于正在等待的human_gate，不能用来把不明结果的running资金节点认证成成功。依赖未成功的节点不能因为用户重复点确认就变为ready。[S10][S11]

#### 5.5.3 状态机与结果未知的边界

:::figure transaction
图5-2 模拟核心交易状态及UNKNOWN结果视图的区别

- **核心交易终态与用户结果视图：**

  核心交易允许created转processing或failed，processing转succeeded或failed，succeeded可转reversed；failed和reversed为当前终态。**UNKNOWN**是外层对尚无法确认结果的描述，不是可以直接写入核心并随意跳转的新终态；它要求核查原交易。核心状态与DAG节点状态不一一同名，应由工具事实及状态归一化函数映射到用户视图。[S03][S06]

- **超时后只查询原请求：**

  例如工具提交后超时，不能假设银行没收到。节点保持待核验语义，恢复时使用原幂等键或transaction_id查询；若查到成功，恢复成功证据；若仍processing或查询异常，继续待核实。**禁止生成新键重发**，也禁止在未确认原结果时补偿上游资金。[S06][S11][S26]

### 5.6 中断、回退与幂等执行

#### 5.6.1 暂停与取消不是同一个动作

- **暂停、恢复与取消的状态约束：**

  pause只在合法任务状态下标记paused，让后续tick停止推进；它不是杀死已在核心受理的调用。resume只允许从paused回到running，human_gate等待必须通过approve路径。cancel先拒绝尚有不明running节点的任务，再进入compensating、跳过待执行节点，最后按已声明补偿处理。[S11]

- **普通计划与延迟任务的恢复差异：**

  恢复普通转账任务时，剩余动作需生成新确认；生日延迟任务则在原已授权范围内恢复。任务暂停后切换配置关闭DAG，不会把已被DAG收养的任务交给旧调度器重复执行；这也是迁移与功能开关测试必须覆盖的执行权边界。[S10][S11][S12]

#### 5.6.2 逆拓扑补偿及“补偿中崩溃”处理

- **逆序补偿与独立幂等键：**

  补偿按拓扑序反向遍历，只处理succeeded且声明compensation的节点。每个补偿使用原节点幂等键加:compensate派生，执行前先保存running补偿记录；一旦已有补偿记录，无论成功、失败还是崩溃中，都不会自动再试。某个补偿失败或未知时停止上游释放，避免下游撤销不明却先解锁依赖资金。[S11]

- **补偿范围与审计关联：**

  生日预算锁可以有明确补偿，已受理鲜花/蛋糕订单或已经转账则不能凭空假设可撤销。逐项回执同时保留execution和compensation结果，因此“取消后没有继续下单”和“过去的订单已经退款”是两个不同事实。当前演示只承诺前者和已实现的声明式补偿。[S06][S10][S11]

### 5.7 持久化一致性与崩溃恢复案例

#### 5.7.1 图快照与审计同事务

- **图快照与事件的原子提交：**

  TaskDagStore复用AuditStore的SQLite连接和锁。在_write中先从字典重建TaskDag做完整校验，确认已有图的trace、actor、plan和intent不变，再更新state_json并逐条写审计事件，最后一次commit；异常统一rollback。state_json保留恢复事实，审计payload保留脱敏事件，两者内容用途不同但提交边界一致。[S12][S41]

## 6. 安全设计与威胁控制

### 6.1 防幻觉、防注入与最小权限

防幻觉首先约束执行与反馈：ToolResult 和核心状态决定数字、受理及成功语义；模型自由文本不填补失败或未知事实。防注入采用规则、受限输出、工具注册、授权复核及攻击语料回归组合，不声称规则能够识别所有隐晦自然语言攻击。[S06][S07][S26]

| 威胁 | 当前控制 | 验证与限制 |
|---|---|---|
| Prompt 请求跳过确认 | 前置检查、受限实体、平台权限独立 | 注入语料与越权测试；非通用攻击识别证明 |
| Agent 伪造金额/来源 | 不可变上下文、平台快照逐项比对 | Supervisor 伪造/冲突用例；非远程证明 |
| 确认重放或替换参数 | token、摘要、身份设备与一次性凭据 | 绑定变更/过期/重放测试 |
| 超时后重复转账 | 稳定幂等键、原状态查询、副作用不重试 | unknown/恢复与并发用例 |
| 隐藏卡片掩盖状态 | 浏览器偏好只保存卡 ID，业务仍读取完整工具事实 | 状态/余额不变及存储异常浏览器测试 |
| 接管假报银行成功 | 固定结论、未知只能待对账、无资金执行接口 | 非法结论与工单事务回滚用例 |

### 6.2 审计链、回放与熔断

关键输入检查、解析、计划、权限、领域核对、确认、认证、工具和任务状态通过 trace 关联。AuditStore 使用 SQLite 哈希链并支持回放与校验，审计身份区分 actor 和 subject；检测证据异常时按原流程冻结高风险操作。[S08][S21][S26]

哈希链提供本地关联与篡改检测，不是银行生产不可篡改存储。恶意主机管理员、存储介质和外部锚定仍是风险，生产需接 WORM/SIEM、留存和访问控制。CircuitBreaker 对连续失败触发锁定；当前运行时共享的锁不是通用租户隔离风控平台。[S08][S09][S29]

### 6.3 受限执行沙箱

独立 Docker 演示仅执行受限整数计算和固定验收探针：无网络、无主机/银行数据库挂载、非 root、只读根文件系统、禁止提权、资源与输出时长配额，结果和摘要进入独立审计与熔断。缺少可信本地镜像或兼容引擎时失败，不降级为宿主执行。[S17]

T07 历史容器专项8场景通过，含导入拒绝、除零、环境隔离、超时、输出、内存及熔断。但它未接聊天任意代码入口或真实 LLM 生成，也不是任意敌对代码的生产隔离认证；容器共享宿主内核。T14 最新整包及目标电脑仍需复验。[S17][S30]

### 6.4 已知风险与生产替换

固定演示 OTP、静态演示会话、Mock 核心、本地终端与本地坐席都不是生产服务。真实 IAM/MFA、设备认证、核心账务、外部渠道、隐私供应商协议、独立红队与安全评估尚未完成；旧全局工具也不能声称通用多租户数据隔离。[S21][S29]

#### 6.5.1 事件规范化与身份信封

- **规范化事件与可信身份信封：**

图6-1 全局序列审计链、身份关联与按trace回放

#### 6.5.2 全局链校验和单任务回放

- **全局链验证与单任务筛选：**

  list_for_trace按全局seq正序返回单任务事件，而verify_trace会读取全局链关系进行校验，再定位目标trace。单任务事件之间可能插入其他任务，因此不能错误地把“该trace上一个事件哈希”当作真实prev_hash。篡改事件内容、身份或链字段应定位断点并按原机制冻结高风险操作。[S08]

- **空轨迹与篡改检测边界：**

  校验空trace可以返回count=0，不能据valid=true就声称已经有审计证据。当前专项验收同时要求相关业务trace非空，避免“没有记录所以没有坏记录”的假通过。已知限制是宿主及存储管理员仍可控制本地数据，生产需要外部锚定、WORM/SIEM和独立权限审查。[S08][S29]

### 6.6 注入、越权与失败关闭

#### 6.6.1 输入检查和执行门槛互相补充

- **规则检查与事实授权互补：**

  前置InjectionGuard在生成领域分析前检查自然语言输入，敏感披露请求也有独立拒绝路径。即便没有识别某个绕过说法，受限实体协议、固定工具注册、PolicyEngine及确认绑定仍不能被字符串中的“我已授权”“跳过认证”替代。因此本项目不把安全建立在提示词自律上，也不把语料测试通过扩展为所有隐晦攻击都能识别。[S03][S07][S13][S49]

- **多入口的身份和权限隔离：**

  跨用户、跨设备、跨会话、家庭代办关系失效及错误坐席操作属于不同授权边界。测试分别在HTTP会话、计划确认、认证凭据、DAG控制、快照及接管状态操作处拒绝；用户只能查询自己的工单，领域模块没有权力给自己加admin字段。[S04][S13][S21][S43]

#### 6.6.2 连续失败与工具/审计故障

- **认证锁定与全局熔断：**

  当前认证最多3次错误后锁定任务凭据，CircuitBreaker还有运行时失败计数和锁定状态。全局熔断复位不应复活已经锁定的凭据；运维解锁也不能把未知银行交易标为成功。工具失败回执不得出现完成交易的数字或流水，审计落盘失败则停止推进而不是静默继续。[S05][S08][S09][S38]

- **故障发生位置决定处理方式：**

  不同故障位置采用不同处理：规划分析失败阻止待执行队列，已经成功的业务工具不因后置分析失败而重新执行；核心unknown进入核查，已知失败才能按明确状态终结；补偿unknown保留在待人工边界，不触发自动重复补偿。[S11][S15][S49]

### 6.7 受限沙箱的执行链与资源控制

:::figure sandbox
图6-2 沙箱宿主控制、隔离容器和结构化回传边界

控制器先做受限AST校验并规范化源码，只做格式构造，不在宿主eval/exec提交代码。Docker启动前核对引擎/镜像平台、不可变image_id及镜像声明卷；拒绝未知镜像卷，确保没有宿主数据、凭据或socket意外进入容器。受限执行与固定探针分开入口，聊天没有自由提供镜像、路径或任意探针源码的接口。[S17]

容器以非root身份、只读根目录、无网络、丢弃capabilities和禁止提权运行，限制64MiB内存、0.5CPU、32PID及共享内存。默认执行监控3秒、最多8192字节输出；异常输出边读取边丢弃超量部分，避免控制器因恶意大量打印无限保留内存。时限、输出和内存探针在容器内验证，不能只看create参数存在就算隔离通过。[S17]

正常计算只接受结构化整数result且限制取值范围；探针要求checks为非空布尔检查且全部为true。退出码0但JSON结构不对仍是INVALID_OUTPUT，清理失败会变为CLEANUP_FAILED，不能把“计算有结果”掩盖为已正确清理。每次随机容器只清理自身，审计起始写入失败不执行代码。[S17]

以上为有限计算语法与固定探针的竞赛隔离演示。T07当时真实容器8场景通过，P11已完成禁网整包验收，当前修订的新镜像文件已校验，但本轮容器复验因Desktop Secrets Engine故障待完成；不开放聊天任意生成代码、不声称真实模型生成质量或生产敌对代码隔离认证。[S17][S30]

### 7.6 浏览器交互实现与异常路径

#### 7.6.1 显示偏好与业务状态隔离

### 9.1 本地知识检索、独立重排和引用

- **资料标准化与权限过滤：**

### 10.1 持久任务单与可信事实投影

- **同库事务与业务状态：**

  原恢复检查点仍是执行依据。business_tasks在保存检查点的同一SQLite事务中更新任务投影，供页面展示目标、约束、事实来源/核对时间、阻塞、责任、授权要求、凭证及时间线。投影只说明进度，不保存可供前端复用的认证凭据或确认权限。查看历史不执行工具，受阻和未提交任务重启后也不会凭记录重新获得付款许可。[S68][S70]

- **执行状态与服务进度分开：**

  支付处理中、未知与待对账保持原请求身份；本地人工排队、领取、结单属于另一类服务进度。ServiceTasks复用HandoffQueue保存交易异议和资金准备记录，不新增银行执行器。银行交易已存在并不能证明用户认可该交易；用户主张也不能直接证明银行差错或退款成功。[S68][S43]

| 对象 | 保存的事实/约束 | 不能据此推断 |
|---|---|---|
| 原生支付任务 | 原任务ID/trace、目标、预检与时间、原请求结果 | 历史确认仍有效、未知可以再扣款 |
| 交易异议记录 | 本人可读交易、固定主张类型、本地case、状态 | 已正式向银行建案、已保护或退款 |
| 资金准备记录 | 目标、期限、保留额、不借款、当前工具缺口 | 自动借款、赎回或未来资金必定到账 |
| 来源参考 | 资料ID/版本/hash/位置、权限核验、是否改稿 | 来源材料拥有资金权限或是银行回执 |

### 10.2 效果范围、确认与认证绑定

- **单次效果描述：**

  action_effects为原单笔支付生成准备契约：主体/设备、金额、收款目录指纹、备注、一次性作用范围、有效期、策略版本与hash、允许的副作用工具以及银行决定的撤销边界。契约是待确认说明，不是授权证明，不修改共享默认账户或新增周期扣款。[S71][S04]

- **签发检查点与写前重验：**

  原确认令牌与认证摘要覆盖效果范围。服务端还要比对持久签发检查点，不能让客户端通过重算JSON摘要替换原金额或收款范围。真正划款前在原核心锁内重查收款目标、预算/保留额、期限和策略；前一条件节点通过不代表以后一直可执行。[S71][S70][S04]

### 10.3 原任务恢复、版本并发与未知结果

- **重准备与新确认：**

  resume_payment只处理允许恢复的原生未提交支付任务。可信会话与设备、任务锁和expected_version共同约束重查；修改金额/收款人/备注/期限或保留额后，仍保留原任务ID与trace，但原确认和原MFA凭据失效。新卡继续走原Planner、实时预检、领域监督和平台权限，不能用“恢复”跳过本人核对。[S70][S71]

- **已提交及未知只查询：**

  已受理、处理中、未知和待对账不创建新幂等请求，不自动重试资金副作用。进程恢复只查询原请求；未能确定时保留未知和人工核查责任，不把超时补写为成功，也不因为本地工单关闭而更新核心交易。[S56][S68][S70]

### 10.4 四域增量与Supervisor核对

- **反诈语义信号：**

  在原风险因子上补充固定词类、共现、否定、引用/教育及正常反例，保存证据与版本。解释性信号不等于诈骗概率；升级权限、保护性暂缓、通知仍由平台规则决定。副作用前实时规则优先，领域Agent不能独立封禁或放行。[S33][S44][S03]

- **财务健康与资金准备：**

  财务工具区分实际消费、现金流与资金占用；在途/重复项按明确关联去重，未来预计、受限资产不当当前可用。资金缺口由当前可用金额减已确认支出及保留额后计算，保留不完整覆盖、未知或过期来源，不能静默当零。资金安排不会触发借贷或申购。[S34][S45][S68]

- **家庭阅读、通知与协助分权：**

  自建身份支持已配置虚构家庭成员分别核准阅读、通知和协助权限，并核对同意版本、额度与期限。撤回后的旧版本不能继续读取或协助。最终付款仍由账户本人完成；亲友称呼不是账户关系证明，关系新增和原授权额度/期限变更仍由可信配置管理。该实现不是生产家庭代付或机构实名认证。[S21][S42][S46][S59]

- **主链事实与冲突保留：**

  Supervisor核对来源、主体/设备、上下文摘要、快照时效和冲突，不用Agent投票覆盖事实。domain_reviews显示可核对事实数与缺失，分析不可用时保留真实工具结果及needs_review；支付补资料使用原恢复细分路径，不能用统一状态覆盖既有澄清和保护性暂缓。[S13][S15][S49]

### 10.5 受控财务条件与原支付DAG

- **只读条件先于副作用：**

  当前cross_domain白名单在原转账前加入financial_health_report与check_funding_ready。后者只读本任务已成功的财务工具结果，核对来源、金额、时间和缺口，拓扑上必须先于原付款步骤；来源未知、过期或不足均拒绝后续动作。客户端approved=true或任意参数不能授权。[S55][S15][S71]

- **账户与业务边界：**

  当前组合只对默认Mock/demo-user提供已授权财务事实。家庭账户或其他银行后端缺对应工具时拒绝，不能移用默认账户财务数据。采纳图撤销旧确认并生成新卡，保留原所有业务步骤、授权、中断/恢复、幂等与声明式补偿；不是任意资金动作自由组合或生产并行调度。[S55][S70]

### 10.6 三类原型的页面与真实责任

- **A：支付异常与人工交接：**

  沿用原自然语言支付链，遇额度、余额或预算阻塞时保存原任务与当时事实。任务页显示阻塞、时间和下一责任，可重新核对或提交同任务人工事项。人工交接包带历史预检事实和来源，过滤账户明细；必须重新核对后才可继续，未提供线上调额申请时明确说明。[S68][S70][S43]

- **B：本人交易异议跟进：**

  用户在任务面板选择本人可读交易并明确主张，可信工具给出交易金额、商户、日期及状态。主张、保护状态、本地工单、银行正式案件号和退款状态分开；当前official_case_id为空、退款未核实。正常事实/异常主张可同时存在，不据此自动冻结卡片或冲正。[S68]

### 10.7 RAG、OCR和音频的来源留证

- **最小参考字段：**

  SourceProvenance在原审计数据库保存来源编号、资料或输入摘要、版本、位置、核对时间与草稿变化标记。OCR字段候选保留行号、位置及置信度，有限数量；音频分别关联上传、PCM、规范化供应商容器及转写摘要。不留存原图、录音或原始聊天正文，不把摘要当签名、说话人身份或真伪鉴定。[S69][S53][S54]

- **关联前及读取时重验：**

  资料必须仍属于同主体/设备可读范围，并与当前资料版本、内容hash、有效期及家庭显式同意匹配。撤权或资料变化后，旧参考只保留最小编号和需重查提示，隐藏失效元数据。公开页面不接受客户端直接上传“银行证据”对象，资料关联不改变原计划确认摘要或赋予副作用权限。[S69][S50]
