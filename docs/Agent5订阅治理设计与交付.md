## 产品目标与特色

依据《用户投诉与需求研究报告》第8节，首版面向有稳定或可预期收入、房租/还款/周期支出的个人用户。长辈和数字操作不熟练者需要通俗、可独立理解的说明；不是默认把他们交给家属代办。

本域帮助用户弄清“扣过什么、以后还扣不扣、服务还能不能用、退款有没有到账”。特色是按所选订阅说明办理影响与未知项，防止把取消当退款、把预期节省当可用余额。属于可验证的产品设计，不宣称行业首创或已获真实用户验证。

## 与整体及其他 Agent 的关系

平台在黄色确认后提供快照；本域只做 analyze/propose，Supervisor 校验来源与候选；取消通过原执行链。金额仍为整数分，facts/evidence 与快照逐项一致。

| 协作者 | 本域承担的工作 | 集成边界 |
|---|---|---|
| 主 Agent | 说明目标缺失、停止扣费条件、服务与退款区别，提供白名单选择/复核/人工建议 | 主 Agent 负责意图、确认和结果呈现；建议不是执行授权 |
| 财务健康、支付域 | 提醒未来节省和待核验退款不能用于当前付款预算 | 不新增余额或节省合计；账本与支付预检仍由对应域及平台负责 |
| 反诈域 | 对未知扣费提供核验路径 | 未知扣费不直接定性诈骗；不根据商户文本执行指令 |
| 家庭域 | 复用平台绑定的 actor/subject | 亲属称呼不产生权限；当前旧订阅源只支持 demo-user |
| 卡片域 | 分别解释扣费授权与卡状态 | 挂失不意味着订阅已取消；没有卡与订阅关联事实，不推断哪些扣费受影响 |

## 本批实现

- 选中目标后，仅用该目标生成退款风险提示，避免其他订阅未知状态污染解释。
- 区分已停止、仍开启、未知、当前渠道不可取消；未知先核实，已停止不重复建议取消。
- 查询成功但空列表只说明当前范围无记录；失败明确未能核实。
- 重复ID不取第一项，缺失/重复ID不作为候选；所有候选仍来自快照。
- 分层解释历史交易、扣费、服务和退款；待处理退款不称到账，不读取当前时间判断服务是否过期。

## 演示与验收

使用虚构快照演示：正常取消建议；已停止扣费但服务记录仍有效且退款未知；不可取消；退款处理中；空列表与查询失败；重复订阅ID。
验收标准：未知/歧义不产生取消步骤；正常请求保留黄色确认；状态解释可追溯；原始事实与证据不变；Supervisor 接受；无银行/网络/数据库副作用。先运行新增测试，原实现出现6项失败，再完成实现。

## 负责人接入事项

## 2026-11-01 两域联合审查修复

本节同时补充[Agent 6 交付说明](Agent6卡片管理设计与交付.md)，记录订阅、卡片与公共平台衔接的本轮变化；两个领域的模块、注册和职责仍独立。

| 审查问题 | 修复后的行为 |
|---|---|
| 否定请求误生成取消或挂失计划 | 否定、办理状态询问、撤销挂失申请进入只读查询；不依赖模型判断。覆盖长句否定，并保留“不见了帮我挂失”的正常办理语义；“取消挂失”识别为解挂 |
| 卡片关键词抢走支付任务 | “给妈妈银行卡转100元”“给妈妈的银行卡转100元”进入转账，收款人识别为妈妈，保留原支付预检、确认、反诈及执行链 |
| 同名卡无法区分 | 可信快照仅增加四位尾号；选择区、普通与长辈模式确认摘要均显示尾号。唯一尾号可定位，重复尾号不默认选卡；显示信息相同的候选不提供办理按钮 |
| 订阅计划提前承诺成功、旧日期被解释为当前有效 | 明确“申请停止”“确认后核验办理条件”；查询和回执区分记录中的到期日与当前服务权益，当前权益由服务商核实 |
| 重复挂失或解挂被报失败 | 领域核验发现目标状态已满足后，通过只读接口再次核验，不调用写适配器；返回“无需重复挂失／无需解挂”。审计记录为 `card.operation.not_needed`，不伪造本次挂失成功事件；复核时状态变化则停止 |
| 只查卡片也要求强认证、强迫选择写操作 | PolicyEngine 将 demo-user 本人的纯查询与未选定目标的查询判为绿色；实际挂失／解挂仍须确认和强认证。查询结果直接说明各卡状态；按钮明确标注“申请挂失／申请解挂”。家庭代办仍保持既有本人认证与人工边界，查询计划不能授权卡片写工具 |

新增回归位于 `tests/test_domain_live.py`，先复现失败后修复；既有订阅和安全测试只更新失真的文案断言，保留授权、状态及资金断言。新增浏览器用例使用隔离数据库，实际点击查询、选择第二张同名卡、认证、挂失、重复挂失、否定查询、拒绝不支持的订阅取消，以及挂失时支付被拦截、解挂后重新确认转账成功；不使用用户已登录的浏览器配置。
