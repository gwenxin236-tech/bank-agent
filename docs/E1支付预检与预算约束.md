# E1 支付预检与预算约束

## 1. 目标与边界

E1 把“能不能办、还差什么条件”变成确认前的结构化只读报告，覆盖可用资金、日累计限额、收款人核验、卡状态、认证条件和预算约束六个维度。每个维度只返回 `satisfied`、`missing` 或 `unknown`，并附事实证据与白话说明。

预检不是银行受理结果，也不是执行授权。确认时仍由 `PolicyEngine` 判定风险与权限，副作用前仍由现有转账工具重新核对余额、日累计和收款人。预检没有修改账户、流水、订阅或核心交易状态的权限。

本项目使用 `MockBankCore` 离线演示。真实生产替换点如下：

- `MockBankCore.balance()`：替换为核心账务可用余额查询；
- `MockBankCore.confirmed_budget_commitments()`：替换为核心账务、信用卡账单和已授权扣款日历的只读聚合查询；
- `MockBankCore.cards_query()`、收款人目录：替换为银行账户与卡片状态服务；
- 预检事件 `payment.preflight`：接入生产审计/WORM 或 SIEM 时保留事实快照与策略版本。

## 2. 结构化输出

`app/preflight.py` 的 `build_payment_preflight()` 返回 `PreflightReport`，其机器视图包含：

```text
checks.available_funds
checks.daily_limit
checks.beneficiary
checks.card_status
checks.authentication
checks.budget
```

每项包含：

- `status`：`satisfied` / `missing` / `unknown`；
- `message`：面向用户的缺口说明；
- `evidence`：整数分、状态和查询来源等可审计事实。

`unknown` 不会被猜成通过。例如，缺少可信卡状态或预算承诺查询时，系统明确展示“未知”，不使用预计收入补足，也不把亲属称呼当成已核验收款账户。

计划生成后、确认前，预检结果同时进入 `plan.preflight` 和 `plan_view.preflight`，并写入 `payment.preflight` 审计事件。账户状态保持不变。

## 3. 预算公式

计划内可支配金额统一使用整数分计算：

```text
计划内可支配金额 = 可用余额 - 已确认支出 - 安全缓冲
本次转账后的预计可支配金额 = 计划内可支配金额 - 本次转账金额
预算缺口 = max(0, -本次转账后的预计可支配金额)
```

已确认支出包括：

1. 结构化演示数据中的本月房租；
2. 结构化演示数据中的信用卡还款；
3. 当前仍有效且待付款的订阅金额。

历史消费不重复计入未来承诺。工资等预计收入的证据字段固定为 `projected_income_cents: 0`，不会增加可用余额或预算额度。安全缓冲读取 `config/policy.json` 的 `preflight_security_buffer_cents`，不在业务代码中另写阈值。

## 4. 缺口处理

当本次转账后的预算为负数，报告会明确显示类似：

> 本次转账会造成预算缺口 ¥X；扣除房租、还款、待付款订阅和安全缓冲后，不会自动借款或擅自降额执行。

计划不会进入可执行确认队列，也不会扣款。返回的用户选择为：

- `adjust_amount`：调整本次金额后重新发起需求并重新预检；
- `adjust_budget`：由用户明确调整预算约束后再重新核实；
- `defer`：延后办理，不执行副作用；
- `human_handoff`：转人工核实。

这些选择只是用户意图，不是绕过权限的开关。服务器仍须重新读取事实并由策略与工具执行前重校验裁决。

确认前若账户或承诺支出发生变化，系统会重新生成预检；若由满足变为缺口，会写 `budget.constraint.blocked`，拒绝确认，账户保持不变。

## 6. 验收边界

本阶段验证的是离线演示级的事实计算、只读性和保护性阻断，不是银行核心账务、授信、真实扣款或灾备验收。金额运算全部使用整数分；本功能不调用外部网络、不引入第三方依赖、不自动借款、不自动降额、不自动重试副作用。
