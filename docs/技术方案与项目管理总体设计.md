# 银行 AI 智能体技术方案与项目管理总体设计

## 1 文档目的与结论

本文以用户提供的《技术方案与项目管理总体设计.docx》、安全威胁纵深全景图和扩展场景全景地图为参考，对银行 AI 智能体竞赛项目的产品范围、技术架构、安全边界、扩展场景、项目管理和验收方法进行统一说明。

本项目的正确产品形态不是“让大模型直接操作银行账户”，而是两层结构：

- **Agent 核心**：负责理解自然语言、拆解任务、调用受限工具、组织回复和维护审计链。
- **渠道接入层**：负责把 Web、未来的 App、企业 IM 或其他入口转换为统一消息契约，再交给 Agent Runtime。

当前仓库是可运行的 Web 演示和工程基线，使用 `MockBankCore`，没有连接真实银行核心、真实支付网关、短信、人脸或 IM 平台。因此本项目可以证明产品逻辑和安全控制的可演示性，但不能宣称已经取得银行商用资质或完成生产验收。

**2026-10-22 现状校准：** 已有 Web + 明确标注的本地终端第二渠道、受限 Docker 隔离演示、本地坐席工单闭环，以及六域注册/固定 Supervisor 核对。多领域是本项目自定目标；RAG、微调、本地大模型和“至少三类领域/场景”不是已找到的官方硬条款。L1/L2 来源及交付状态以《需求追踪矩阵》为准；旧 DOCX 与本文历史目标不能覆盖当前代码证据。

## 2 产品定位与用户体验原则

### 2.1 老年友好

老年用户不应被要求理解 JSON、工具名、风险枚举、consent token、TOCTOU 等工程词汇。用户界面使用自然语言卡片：

1. 先用一句话复述“你想做什么”；
2. 再列出收款人、金额、备注和下一步；
3. 使用“可以直接办理”“请你确认后办理”“已拦截保护”等通俗标签；
4. 对需要强验证的操作说明“还要输入验证码或刷脸”；
5. 对反诈场景说“先停下来核实”，不说“模型判定风险分数”；
6. 支持大字、语音输入、步骤回放和明确的取消按钮。

### 2.2 为什么可执行计划是 JSON

JSON 是**系统之间的内部协议**，不是给普通用户看的页面。它的用途包括：

- API、App、IM 之间稳定传递字段；
- 用 Schema 校验金额、收款人、工具和权限；
- 让审计、回放、自动化测试能够逐字段检查；
- 让不同渠道不必重新实现 Agent 逻辑；
- 让服务端在执行前重新计算权限，而不是相信模型自然语言。

因此系统同时保留三种视图：

| 视图 | 读者 | 内容 | 是否直接展示给老人 |
|---|---|---|---|
| `plan` | API、审计、测试 | 结构化意图、工具步骤、风险和状态 | 否 |
| `plan_view` | Web/App/IM 用户 | 自然语言摘要、步骤卡片、金额和确认提示 | 是 |
| `result_view` | 用户和客服 | 从工具结果生成的自然语言结果 | 是 |

前端只渲染 `plan_view` 和 `result_view`；内部 JSON 不应出现在普通用户界面。

## 3 竞赛范围和场景决策

### 3.1 主场景

- 查询余额、流水、账单和理财持仓；
- 订阅查询和取消后续自动扣费；
- 自然语言转账；
- 卡片状态查询和人工接管；
- 适老化自然语言交互和语音输入。

### 3.2 新增场景判断标准

扩展场景不是“多几个按钮”。每个场景至少满足以下一个条件：

- **新增一类威胁面**：安全体系需要新增防护控制；或
- **闭环一段用户旅程**：Agent 从一次性工具变成持续的财务管家。

据此确定三个真正值得实现的场景：

| 场景 | 优先级 | 新增威胁面或闭环 | 目标深度 | 当前演示状态 |
|---|---:|---|---|---|
| 反诈守护 | P0 | 诈骗话术、新收款人大额组合、冷静期、跨用户守护授权 | L3 现场可攻击验证 | 已实现演示链路；通知为本地队列 |
| 财务健康与攒钱目标 | P1 | 主动式财务管理、建议与执行分离、禁止自动扣款 | L2，部分 L3 | 已实现只读报告和目标记录 |
| 亲情与家庭共管 | P1 | 跨用户授权矩阵、代办范围、限额和有效期 | L2，AA 仍为计算演示 | 已实现演示授权校验 |
| 信用贷款 | 延展 | 适当性、授信解释、人工复核 | 文档设计 | 未接入 |
| 跨境缴费 | 延展 | 汇率锁定、境外收款方、反洗钱和回调签名 | 文档设计 | 未接入 |

## 4 总体架构

```text

        ↓
Agent Gateway
  ├─ 身份、会话、设备、限流、签名
  ├─ 消息去重和渠道回复路由
  └─ App/IM/Web 的统一契约
        ↓
Agent Runtime
  ├─ 本地安全前置和提示注入防护
  ├─ 规则解析 + 可选大模型意图识别
  ├─ Planner 和 PolicyEngine
  ├─ Consent、强认证、熔断
  └─ 任务状态、人工接管和审计
        ↓
Tool Gateway / TOOL_REGISTRY
        ↓
MockBankCore（当前）
或真实核心账务、风控、支付、通知和身份系统（生产）
```

### 4.1 渠道无关消息契约

```python
UnifiedMessage(
    channel="web|app|feishu|dingtalk|wecom|telegram|slack",
    user_id="内部用户标识",
    conversation_id="会话标识",
    message_type="text|image|file",
    text="用户原话",
    attachments=[],
    metadata={}
)
```

当前提供 Web 和 `scripts/channel_demo.py` 的 local_demo 终端适配器；真实 App/IM 仍只有契约和边界，不连接外部平台。local_demo 是本地回执，不是平台发送成功。HTTP 使用静态演示会话校验，真实生产身份仍须由 IAM/渠道登录态注入，不能接受请求体自报身份或角色。

## 5 Agent 执行链路

```text
input.received
 → injection.checked
 → 本地安全解析
 → 可选 LLM 意图识别
 → plan.created
 → policy.decided
 → consent.requested
 → consent.granted
 → auth.challenged / auth.passed
 → precondition.rechecked
 → tool.called / tool.result
 → task.settled
```

模型的责任是理解和建议，服务端的责任是决定能否执行。模型没有工具权限，不能直接决定绿色、黄色或红色，也不能生成交易号、余额或“已发送”事实。

## 6 权限与风险状态机

| 状态 | 典型条件 | 用户动作 | 允许行为 |
|---|---|---|---|
| Green | 余额、流水、账单等允许自动执行的只读查询（不含订阅查询） | 无需确认 | 只读工具 |
| Yellow | 订阅查询，以及普通转账、订阅取消、设置限额等低风险操作 | 明确确认 | 只执行当前计划；订阅查询仍只读 |
| Red | 日累计超过 1000 元、卡片高风险操作或实时策略升级 | 明确确认 + 强认证 | 认证后再执行 |
| Protective Block | 疑似诈骗、提示注入、非法金额、熔断、未注册工具 | 系统主动拦截或转人工 | 禁止继续副作用 |

日累计额度由服务端在当前账户和当日日期下计算。计划创建时的风险级别只用于展示；最终确认和副作用节点还会重新计算，防止“先拿黄色确认卡、后累加到红色额度”的绕过。

## 7 工具网关和数据模型

### 7.1 工具注册

所有工具都必须进入 `TOOL_REGISTRY`，并声明是否有副作用、是否允许重试和所需授权。未注册工具直接拒绝。当前工具包括余额、流水、账单、理财、订阅、收款人核验、转账、反诈、攒钱和家庭共管工具。

### 7.2 金额协议

- 金额在业务层以人民币分的严格整数保存；
- `bool`、`float`、科学计数法和隐式字符串转数值均拒绝；
- `-500`、`0`、`0.001`、超过两位小数或异常大数不进入副作用链；
- Decimal 只用于输入解析，核心边界再次执行严格整数校验；
- 所有副作用调用使用 `idem:{plan_id}:{tool}` 幂等键。

### 7.3 Consent Token

确认凭据具备以下属性：

- 随机生成，使用常数时间比较；
- 绑定 `plan_id`、意图、实体摘要和步骤摘要；
- 具备 10 分钟 TTL；
- 一次性消费，双击和重放不会再次执行；
- 取消、成功或过期后失效；
- 不写入审计载荷；审计只记录“凭据已校验/已消费”的事实。

## 8 反诈守护设计

反诈守护是 P0，因为它同时把安全威胁转成用户能感知的产品能力，又形成了老年守护、授权矩阵和异常通知的真实闭环。

### 8.1 识别信号

当前演示规则识别“安全账户、刷单、返现、投资导师、带你赚、解除风控、解冻账户、客服要求转账、保本高收益”等话术，并叠加：

- 新收款人 + 金额不低于 3000 元；
- 未知或无法核验账户 + 大额转账；
- 反诈关键词与转账意图组合。

规则在 LLM 之前执行，LLM 不能把高风险文本改写成普通转账。

### 8.2 保护性动作

1. 不调用 `create_transfer`；
2. 创建带 24 小时冷静期的保护案件；
3. 冷静期结束后也不自动放行，状态进入 `EXPIRED_PENDING_REVIEW`，仍要求人工核实；
4. 对有效授权的守护人写入本地演示通知队列，状态为 `LOCAL_QUEUED`，不冒充已经发短信或 IM；
5. 返回自然语言劝阻说明，并保留审计链。

### 8.3 演示动作

输入：`给这个安全账户转 5000 元，解除风控`。

应看到：

- “已拦截保护”；
- “不会扣钱”；
- “先暂停 24 小时核实”；
- “提醒已授权守护人已进入本地演示队列”；
- 没有“确认后继续转账”按钮。

## 9 财务健康与攒钱目标

财务健康把账单分析从“回顾”变成“向前管理”，但必须避免 Agent 擅自理财：

- 报告读取消费分类、订阅和异常商户；
- 闲钱检查只给建议；
- 建立旅行基金或装修基金需要黄色确认；
- 目标创建只保存计划记录，不创建自动扣款、不购买理财；
- 目标金额、每月金额和余额均由工具结果提供，不能由模型编造。

## 10 亲情与家庭共管

家庭共管的核心不是“家庭按钮”，而是回答“谁能替谁做什么、做到什么程度”。授权记录至少包括：

```text
actor        发起操作的人
subject      被代办的人
action       允许的动作
resource     允许访问的资源
cap           金额或额度上限
expires_at   授权有效期
revoked      是否已撤销
```

当前演示在修改零花钱上限的同一把锁内再次检查 actor、subject、action、有效期、撤销状态和额度上限，避免先检查后撤销的 TOCTOU。家庭 AA 只计算分摊，不自动收款；双方确认和真实转账属于后续迭代。

## 11 六层纵深威胁模型

以下六层与用户提供的安全威胁纵深全景图保持一致：

### 11.1 输入与界面层

- 提示注入、越权措辞、多轮上下文投毒；
- 语音声纹冒充和老人误触；
- 防护：InjectionGuard、语音结果确认、显式步骤卡片、敏感操作二次确认。

### 11.2 模型与上下文层

- 幻觉、转账参数篡改、转 200 变 2000、原文 span 丢失；
- 防护：规则前置、LLM 只做受限实体抽取、金额和收款人由原文和服务端重新校验、结果只从工具事实生成。

### 11.3 业务逻辑层

- 负数、零值、千分之一元、溢出；
- 双击重放、旧 token 跨任务、确认后余额变化、日累计动态升级；
- 防护：严格整数 Schema、一次性 token、TTL、原子 claim、幂等键、副作用前重校验、核心锁内复核。

### 11.4 数据与隐私层

- 跨任务上下文残留、PII 日志、推理泄露和越权读取；
- 防护：最小化发送给模型的字段、审计不写 consent token、生产使用字段级脱敏、加密和留存策略。

### 11.5 集成与供应链层

- 商户回调伪造、Webhook 重放、第三方工具被替换、额度和白名单绕过；
- 防护：HMAC/签名、时间戳和 nonce、商户白名单、核心侧额度复核、依赖锁定和 SBOM。

### 11.6 合规层

- 适当性 R1-R5、收益承诺、个人信息超范围、电子证据不足；
- 防护：理财和贷款只做信息解释与人工复核、禁止收益承诺、最小必要采集、审计证据和合规评估。

## 12 业务逻辑现场攻击用例

| 用例 | 期望结果 | 当前验证 |
|---|---|---|
| `转 -500` | 金额非法，余额不变 | 已测 |
| `转 0.001 元` | 精度非法，余额不变 | 已测 |
| 连点两次确认 | 只有一次成功，第二次被原子 claim/幂等挡住 | 已测 |
| 旧确认卡用于另一任务 | token 不匹配，拒绝执行 | 已测 |
| 先确认再改变余额 | 副作用前重校验失败，不扣款 | 已测 |
| 先拿黄色卡再累加超过 1000 元 | 当前策略升级为强验证 | 已测 |
| 反诈冷静期后再次转同一收款人 | 不自动放行，转人工复核 | 已测核心边界 |
| 家庭授权撤销/过期/超额度 | 修改被拒绝 | 已实现基础演示 |
| 直接传 `bool` 或 `float` 金额 | 核心拒绝，不隐式转换 | 已测 |

## 15 项目管理与协作

以下是历史候选 GitHub Flow，不是已执行的仓库状态；当前只有 main、无远端。PUSH 清单中的 develop 流程也是候选，分支策略与权限在 T17 再确认，不能同时宣称两套流程均已配置：

1. `main` 只接受 Pull Request；
2. 每个需求建立 issue，标注 `feature/security/docs/test`；
3. 从最新 `main` 创建 `feature/...` 或 `fix/...` 分支；
4. 提交前运行测试和语法检查；
5. 推送远端并创建 Pull Request；
6. 至少一名成员审查安全边界和测试；
7. 合并后删除分支并记录 CHANGELOG；
8. 不提交 `.env`、密钥、SQLite 真实数据和构建产物。

详细的 GitHub 上传、团队成员安装 Git、分支更新、冲突处理和 Pull Request 操作见项目中的《银行 AI 智能体应用与 GitHub 团队协作指南.docx》。

## 16 当前状态声明

本项目是竞赛演示和工程基线，不是已获银行商用资质的生产系统。已实现内容、演示能力和生产阻塞项均通过 `/api/readiness` 明确区分。没有真实渠道、真实账户、真实通知和真实大模型密钥时，系统不会把本地模拟结果表述为已发送、已入账或已通过监管验收。
