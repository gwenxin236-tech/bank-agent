# E5 人工交接与凭据路径

## 1. 目标与边界

E5 将“转人工”从一句提示升级为结构化的最小必要信息交接卡，保证人工继续办理时能够看到用户目标、已经核实的事实、授权边界、已经执行的步骤和待处理事项，而不要求用户重新复述全过程。

本项目仍是离线竞赛演示与工程验证平台。当前交接卡写入本地 SQLite 审计链并在网页人工客服面板展示；它不是正式客服工单，也不是银行正式凭据。生产替换点是银行 CRM/客服工单系统、统一身份认证系统及其字段级数据防泄露策略。

## 2. 交接卡字段

| 字段 | 含义 | 演示实现 | 生产替换点 |
| --- | --- | --- | --- |
| `user_goal` | 用户希望办理的目标 | 来自已生成计划的摘要/意图，主动求助时为“用户主动请求人工帮助” | 使用可信会话中的用户目标摘要；不得直接把聊天原文转发给坐席 |
| `verified_information` | 已核实且继续办理所必需的事实 | 收款人、整数分金额、订阅/家庭成员等结构化事实 | 由核心/账户服务返回并标注核实时间、来源和有效期 |
| `authorization_scope` | 本次允许人工继续核验的范围 | actor、device 和“仅限本次计划”说明 | 由 IAM/授权服务签发短时、最小权限 case scope；不能把交接卡当授权凭证 |
| `executed_steps` | 已完成或已执行的步骤 | 只列步骤 ID、工具/业务动作和状态，不带工具原始返回全文 | 关联核心交易号、工单步骤和操作员回执 |
| `business_identifiers` | 业务追踪标识 | `trace_id`、`plan_id`、`dag_id`、可获得的交易号 | 映射到核心交易、支付网关、客服工单和 SIEM 的关联 ID |
| `pending_items` | 仍需人工确认或处理的事项 | 例如“核验原请求结果；不自动重发副作用” | 由业务状态机和人工队列生成，不由模型自行改写 |
| `redacted_context` | 必要的、已脱敏的上下文 | 触发原因、DAG 状态、整数分金额、办理路径提示 | 采用银行数据分级、最小化披露和留存删除策略 |

### 脱敏规则

- 卡号/账户号只保留后四位，展示为 `****1234`；
- 金额保持整数分（例如 `300000` 表示 3000 元），不在交接卡中做浮点换算；
- 原始对话、聊天记录、系统提示词、验证码、密码、token、CVV 等不进入交接卡；
- 前端使用 HTML 转义后渲染交接字段；
- 审计事件只挂载已经脱敏的交接卡，不记录原始输入。

## 3. 三类触发路径

1. **人工确认节点拒绝**：用户拒绝当前确认计划时，生成 `human_gate_rejected` 卡，记录已经核实的计划和仍待处理事项；不执行后续副作用。
2. **结果未知转人工**：交易结果处于未知/处理中且用户选择转人工时，生成 `unknown_result` 卡，明确要求人工核验原幂等请求；系统不自动重发转账。
3. **用户主动求助**：点击“一键人工客服”或适老化的人工帮助入口时，生成 `user_requested` 卡。系统只记录本地请求，不假称已接通真人。

三类路径均写入 `human.handoff.created` 审计事件，并沿用现有审计哈希链。交接卡生成失败不会阻塞已经记录的客服请求；这保证辅助证据不可用时，原办理流程仍可安全返回。

## 4. 前端查看路径

打开演示首页，点击顶部“一键人工客服”或反诈提示中的“请人工帮我核实”。请求记录成功后，页面会显示“给人工客服的交接卡”，包含：

- 用户目标；
- 已核实信息；
- 授权范围；
- 已执行步骤；
- 业务与交易标识；
- 待处理事项；
- 已脱敏的必要上下文。

页面明确提示：这是演示系统提供的办理路径，不生成正式银行凭据。人工继续办理仍必须通过银行官方渠道重新核验身份、设备、授权范围和业务事实。

## 5. 凭据获取路径：诚实边界

演示系统可以提供 `trace_id`、`plan_id`/`dag_id`、交易号（如工具已经产生）以及待核验事项，用于现场回放审计和说明办理路径；它不会伪造短信验证码、正式授权书、银行回执或客服工单号。

真实业务中，用户应通过银行官方 App、银行卡背面官方客服电话或已认证的人工坐席获取正式凭据和最终回执。演示系统中的交接卡只说明“下一步应由哪个官方流程核验什么”，不替代真实银行的身份认证、授权签名、核心账务查询或人工工单系统。
