# C2 — 反诈风控闭环与通知总线

交付日期：2026-09-21。范围：离线、Python 标准库、SQLite 本地持久化的银行生产替身；不是已接入银行风控、真实反洗钱平台或通知供应商的生产系统。

## 1. 决策链与风险口径

```text
用户输入 → 本地资金意图解析 / 话术匹配
         → PolicyEngine（既有权限规则 + 可信特征 + 评分 + AML）
         → 计划 / 再确认复检 / 副作用前持核心锁复检
         ├─ 风险分 ≥60：暂缓、无扣款、审计、通知总线
         ├─ 既有反诈硬规则：识别、冷静期、通知，不创建转账
         ├─ AML 命中但分数 <60：红色、确认 + 强认证
         └─ 其他：仍遵循既有单笔及日累计额度、权限和强认证规则
```

`app/risk_controls.py::score_transaction_risk` 只计算特征，不裁决执行权限；唯一裁判仍是 `PolicyEngine.classify`。金额以整数分计算，不接受布尔、浮点或非正数。

| 特征 | 加分 | 本地可信来源 |
|---|---:|---|
| 新收款人 | 30 | 收款人不在核心替身的已知收款人表中 |
| 金额 ≥1000 元（100000 分） | 20 | 本地解析并校验的金额 |
| 命中话术库 | 50 | 既有 `config/fraud_rules.json` 规则；同时命中多条只加一次 |
| 老年用户 | 20 | 服务端 `MockBankCore.user_profiles`；默认用户未标记为老年 |
| 30 分钟内第 3 笔及后续转账 | 30 | 同用户已有两笔及以上核心 `succeeded/processing` 记录 |

窗口包含恰好 30 分钟的边界，排除未来时间。已失败、已冲正的交易不计数。生成计划、双击和幂等重发不会新建核心记录，因此不增加笔数。`processing` 计数用于保守风险判断，不等同于已成功扣款。

客户端提供的 `risk_score`、`is_elderly`、`is_new_recipient` 不用于覆盖服务端特征。新收款人表、年龄标记和家庭授权仍是演示档案，不提供客户端任意修改 API；未登记的新收款人即使未达暂缓阈值，仍会被既有收款人核验阻止执行。

计划与 `policy.decided` 保存 `risk_score/risk_factors/recent_transfer_count/aml_count/aml_suspect/decision_reason` 等证据。确认时和实际转账前重新计算；执行前评分与核心受理共用核心锁，避免并发确认穿过风险窗口。副作用工具不自动重试。

### AML 最小规则（明确的演示假设）

“接近且低于 1000 元”在本交付中定义为 **900 元 ≤ 单笔金额 <1000 元**，即 `[90000, 100000)` 分。同用户、同日已有两笔该区间的 `succeeded/processing` 交易，当前候选成为第三笔时命中；可以跨收款人统计。默认日界与现有账务演示保持一致，使用 **UTC 日**，不是设备本地日期。

命中写入 `aml.suspect`，`decision_reason` 包含拆分笔数和规则原因。若风险分小于 60，则升级红色、必须再次确认并完成强认证；本任务没有把所有 AML 命中自动等同于冻结或拒绝。三笔各 900 元给已知收款人：第一笔按原策略，第二笔因日累计升级强认证，第三笔增加连续转账 30 分、命中 AML 并保持红色。只有认证后再次确认才能执行。

这只是可演示的风险线索，不是监管认定或真实可疑交易报送；区间下限、日界、交易状态口径与是否转人工必须由生产风控/合规团队配置和审批。

## 2. 通知总线、审计和查询

`app/notification_bus.py::NotificationBus` 使用审计库的 SQLite 连接和可重入锁，持久化订阅、事件、通知回执。

| 发布事件 | 触发路径 |
|---|---|
| `transaction.deferred` | 评分暂缓、反诈冷静期、核心仍为 processing |
| `fraud.blocked` | 既有反诈保护流程创建冷静期后 |
| `auth.failed` | 验证码错误、凭证失效/重放/绑定错误等认证拒绝 |
| `device.risk` | 确认或认证时提交的设备与计划绑定设备不一致 |

默认 App 推送和短信各有一个本地模拟订阅；有有效家庭授权时注册守护人订阅。`subscribe(user_id, channel, target, event_types=None)` 可在服务端配置订阅的事件类型，渠道为 `app_push/sms/guardian`，不存在对外任意发布事件的 HTTP 接口。

守护通知检查既有演示矩阵中的 actor、被守护对象“妈妈”、`receive_fraud_alert`、未撤销及有效期，然后映射到“女儿”演示身份。无授权时不创建守护订阅；已有订阅后撤销时，通知状态为 `SUPPRESSED` 并写审计。恢复尚未完成的分发也会重新校验授权。**高风险用户只有存在有效守护授权才通知家人，不能因风险高绕过家庭授权。**

状态 `LOCAL_QUEUED` 仅表示本地队列和审计已记录，不表示 App、短信或家人真实收到。原 `notify_guardian` 工具只引用已审计总线回执，不再单独生成另一条发送队列。已完成的历史回执不会因后续撤权改写，也不代表仍可再次发送。

证据链：

```text
policy.decided / aml.suspect / transaction.deferred / auth.failed / device.risk
 → notification_events（事件幂等键）
 → event.published（审计）
 → notifications（事件 × 订阅唯一）
 → notification.queued 或 notification.suppressed（审计）
 → 通知查询可见
```

通知 ID、事件 ID 用无数字 UUID 编码保持与脱敏审计的关联；不对手机号、卡号、身份证、验证码设置脱敏豁免。通知 payload 在入库前经过既有 C5 脱敏，HTTP 输出也脱敏；验证码不进入通知原因。通知审计携带用户、任务、设备、操作、风险原因和关联 ID。

### 查询接口（本地演示）

| GET 路径 | 参数 | 返回 |
|---|---|---|
| `/api/v1/notifications` | 必填 `user_id`；可选 `trace_id/channel` | 已审计回执：ID、事件、渠道、目标、状态、脱敏 payload |
| `/api/v1/notifications/events` | 必填 `user_id`；可选 `trace_id` | 持久事件，可包含尚在恢复分发的事件 |
| `/api/v1/notifications/subscriptions` | 必填 `user_id` | 订阅与事件类型 |

统一响应包含 `ok/mode/count/items`，`mode=local_simulator`；缺用户或不支持的渠道返回 400。示例：

```bash
curl 'http://127.0.0.1:8090/api/v1/notifications?user_id=demo-user&channel=guardian'
curl 'http://127.0.0.1:8090/api/v1/notifications/events?user_id=demo-user'
curl 'http://127.0.0.1:8090/api/v1/notifications/subscriptions?user_id=demo-user'
```

**`user_id` 只是本地筛选参数，不是登录认证。接口不具备生产跨用户访问隔离，不能暴露到公网或接入真实个人数据。** 生产必须从认证会话取得主体，以 RBAC/ABAC 限制用户、守护人及运营人员的查询范围，不能信任查询参数自报身份。C2 未新增前端页面，可通过接口或测试现场查询证据。

## 3. 持久性与故障边界

- 相同用户、相同事件幂等键只建立一条事件；同事件、同订阅只建立一条通知。事件键不允许挪给不同事件类型或不同 trace。
- 总线在启动时补完 `complete=0` 的事件；通知只有补完审计才进入通知查询结果。审计故障向调用方报错，不伪造已通知成功。
- 审计写入后、完成标记写入前崩溃，恢复可能追加重复审计，需按通知 ID 关联；**不声称端到端 exactly-once**。
- 核心账务与事件总线不是跨库原子事务。核心受理后、发布事件前进程崩溃，可能缺通知事件；当前恢复只保证已持久事件的分发恢复，生产需事务 outbox、对账补偿。
- 核心 `processing` 的风险事件不改变 C1 事实源；用户仍看到“银行还在确认这笔交易，请不要重复操作”。总线恢复绝不重新调用转账。
- 核心记录和总线数据持久化；演示年龄、已知收款人和家庭授权仍由启动时的模拟档案提供，临时修改不会持久化。生产必须由持久且可撤销的权威服务提供，不能把重启默认授权当成真实授权恢复。
- 单进程锁用于本地并发一致性；本任务不保证多实例风控并发、跨库事务或真实供应商送达语义。

## 4. 真实生产替换点

| 模拟实现 | 替换点及上线条件 |
|---|---|
| `user_profiles/bank.beneficiaries` | 实名客户、设备与收款人画像服务；特征版本、来源、更新时间可审计 |
| `assess_transfer_risk` 扫描本地账务 | 核心/支付网关查询 Adapter、按用户的持久实时特征、统一业务日/时钟与窗口计数；不能从模型取交易事实 |
| 固定评分和 AML 区间 | 经审批的版本化风控规则、AML 调查与人工处置流程；策略权限裁判保留在服务端 |
| `guardian_target` 演示授权矩阵 | 实名守护关系、持久授权/撤权、有效期、事件级数据最小化；收件人由权威授权服务取得 |
| SQLite 事件表 | 事务 outbox 与可靠消息中间件，消费者幂等、失败重试/死信、事件对账和多实例并发控制；不得重试银行副作用 |
| App/短信/守护本地队列 | Push/SMS Adapter、供应商认证、发送许可、限频与真实送达回执；家人只看到授权范围的数据 |
| 本地审计哈希链 | 沿用 C5 的 WORM/SIEM 与密钥管理替换点，安全事件告警及通知证据集中关联 |
| 按查询参数筛选 | 强身份网关、租户隔离、RBAC/ABAC、访问审计、字段脱敏和留存策略 |
