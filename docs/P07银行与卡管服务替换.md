# **P07 银行与卡管服务替换边界**

## **1. 目标与当前结论**

### **1.1 需求分层**

- **L3团队目标**：完成银行/卡管适配、协议与故障测试，复用当前代码，不让成员领域Agent接触银行凭据或直接执行工具。工作表依据《五人团队Agent接入契约》第9节P07及9.1。
- **L1安全约束**：原三色权限、确认、强认证、审计、熔断、DAG中断和人工接管继续生效；受理、处理中、未知和成功分开，副作用不自动重试。银行服务结果不是模型可以补写的事实。
- **完成边界**：基础批是规范化协议及HTTP替身验收；其后已接入独立的Apache Fineract/PostgreSQL开源核心，实际转账、原生回调和撤销结果见第6节。真实银行/支付网关/卡管平台仍未选定，没有银行授权账户、机构证书或正式对账单，因此仍不标“真实银行已接入”。

## **2. 接口与可信账户上下文**

### **2.1 复用与新增**

- **复用契约**：`app/production_contracts.py`原`AdapterContext/AdapterResult`及`BankCoreAdapter/CardManagementAdapter`。Context在原字段之后增补`subject_id/account_ref/authorization_ref/authorization_version/operation_digest`，均有兼容默认值；旧Mock调用可继续工作，但真实服务边界不接受空授权字段。成员DomainContext/Finding/Proposal ABI不变。
- **实现**：`app/bank_service.py`的`BankServiceAdapter`实现余额、转账、原交易查询、显式冲正边界和卡管三方法，并提供`query_by_idempotency/apply_callback/reconcile_statement`。业务调用不需要引入第三方依赖。
- **传输替换点**：服务端注入`transport.send(operation, request, timeout_seconds)`，必须由实现者处理受信地址、认证/TLS/mTLS、超时、响应体限制和供应方状态归一化；传输层本身不得重试写请求。本批只实现并测试回环HTTP替身，不提供可连接任意银行的通用凭据或公网URL入口。

### **2.2 主体与授权绑定**

- **可信映射**：`BankBinding`由平台构造，包含actor、subject、账户引用、授权引用与版本、允许设备、已核验收款人映射及卡片集合。`authorization_ref`是非秘密引用，不是访问令牌或已完成真实认证的证明。
- **拒绝条件**：未知主体、跨设备/账户、授权引用或版本不一致、未绑定收款人/卡片、金额为bool/浮点/非正整数、缺幂等键或操作摘要均在提交前拒绝。只支持本人账户，家庭代办不沿用演示授权扩大外部账户权限。
- **真实授权仍缺**：当前映射与认证是受控测试夹具，未接真实IAM、银行账户归属核验或银行侧交易授权。P09完成及供应方授权落实前，不能把本地字段校验当作真实金融身份认证。

### **2.3 项目规范化协议v1**

| 部分 | 字段与约束 |
| --- | --- |
| 请求 | `schema/operation/request_id/actor_id/subject_id/account_ref/authorization_ref/authorization_version/device_id/trace_id/operation_digest/idempotency_key/payload`；身份与业务参数由平台绑定 |
| 回执 | 精确字段`schema/operation/request_id/actor_id/subject_id/account_ref/idempotency_key/provider_request_id/status/sequence/payload`；原请求及主体/账户必须匹配，状态序号为正整数 |
| 余额payload | `available_cents/daily_transfer_cents/currency/as_of`；整数分、CNY、带时区，最多60秒旧、最多5秒未来偏差 |
| 转账payload | `amount_cents/currency/beneficiary_id/transaction_id`；与已绑定请求相同，服务方交易引用独立保存 |
| 卡管payload | `card_id/card_status`；只允许normal/reported_loss，成功挂失/解挂回执还须符合目标状态 |
| 状态映射 | accepted/created→processing；processing/unknown/succeeded/failed/reversed保持独立语义；未知状态、额外字段、错账户或错金额不采信 |

- **非行业标准声明**：上述字段是本项目适配层的内部协议，不能照搬为某家银行官方API。供应方正式协议到位后应新增对应Transport/SDK映射并独立验收。
- **两个引用**：应用生成稳定本地`bankreq_`引用；服务方请求/交易引用仅来自校验成功的回执，响应丢失时保持缺失，不伪造银行交易号。对用户返回的transaction_id是本地查询引用，不能当作正式银行凭证。

## **3. 幂等、未知与只读恢复**

### **3.1 持久受理台账**

- **先记后发**：SQLite `bank_requests`先持久预留幂等键、原上下文、业务指纹和本地请求引用，再调用服务。指纹绑定操作、账户、设备、授权版本、摘要和业务参数，原始note不写通用审计，但作为必要请求台账字段保存。
- **禁止重发**：同键同指纹返回已有记录，同键改金额/目标/身份/操作拒绝；进程重启不会再次提交。并发唯一约束避免两次写受理。传输异常、无效回执、提交后的审计或存储异常都不证明银行未执行，保持unknown并保留本地引用。
- **可用性取舍**：如果预留后、真正发送前崩溃，也不会自动重发，可能需要人工核查“未找到原请求”。这是本地至多一次发送策略，不是对银行原子扣款、分布式恰好一次或跨主机一致性的认证。银行端仍必须有持久幂等能力。
- **存储与审计**：预留失败或提交前审计失败不发送。已有哈希链审计记录受理、读取、回执核对、回调与对账事件；本地台账属于敏感业务元数据，随受保护数据库保存，不对领域Agent或普通HTTP用户开放。生产留存期限、加密与备份由后续部署策略决定，本批不虚构法定期限。

### **3.2 查询与恢复**

- **原请求查询**：`query_transaction`只接受本地已有、归属正确的请求；`query_by_idempotency`找到同一记录后只读查询。查询不可用或状态冲突返回unknown，不能推断成资金失败；已有终态不被较旧或矛盾状态覆盖。
- **主链恢复**：`AgentRuntime`通过`ProtocolBankFacade`保留原执行路径和DAG幂等键；原恢复器读取服务台账而不是模拟账务表。响应丢失后重启只查询，不重转；卡管待处理时不继续最终状态验证或写“已挂失”，查清后剩余步骤仍按原人工确认/认证流程继续。
- **冲正**：默认明确`REVERSAL_NOT_SUPPORTED`，不开放聊天或DAG自动冲正工具。只有平台显式支持、原交易成功、独立幂等键及受权上下文齐备时才允许协议级调用；实际退款/冲正、可撤销条件和银行支持仍未验收。测试夹具的冲正回执不代表真实资金已退回。

## **4. 回调与对账**

### **4.1 内部回调适配方法**

- **校验**：`apply_callback(raw, signature)`要求预配置至少32字节密钥，对原始字节HMAC-SHA256验签；事件含event_id、issued_at和规范化receipt。时间窗口300秒，拒绝重复JSON键、超长、伪签名、跨账户、未知原请求、过期、同事件改内容、序号倒退及终态回退。
- **幂等与权限**：事件去重记录持久化；重复相同事件只确认接收，不提交银行业务。回调只更新经过核对的原请求回执，不授予确认/认证，也不让人工结单变为银行成功。
- **当前边界**：这是项目内部协议的适配方法，**没有开放公网银行回调HTTP路由**，不代表已实现某家银行签名、证书轮换、密钥托管、多实例事件总线或回调生产认证。正式服务应按其文档替换验签方案。

### **4.2 只读请求级对账**

- **对照范围**：服务返回当前账户规范化请求回执集合，与本地台账对比账户/金额/收款人、请求与服务方标识、状态、序号、重复、银行侧有/本地无及本地有/银行侧无。最多1000条；当前不是完整银行流水分页、余额试算或财务日终总账对账。
- **结果**：`MATCHED/MISMATCH/PENDING_REVIEW/UNAVAILABLE`区分一致、差异、仍有未决和取数不可用；返回差异与未决数量。只出报告，不自行补转、退款、改账或将未知变成功。
- **HTTP入口**：受信会话下GET `/api/v1/bank/capabilities`显示MOCK或LOCAL_PROTOCOL_TEST，`live_bank_connected/production_ready=false`；GET `/api/v1/bank/reconciliation`只读核对本人的协议账户。默认Mock未配置时返回503，不编造对账成功；不把该接口直接接到尚未确定的外部银行。

### **6.2 实际接入与安全边界**

- **实现**：`app/fineract_transport.py`的FineractAPI只连接字面环回地址，不跟随重定向；凭据只在私有运行配置/内存。Transport将项目协议映射到原生API，精确Decimal转整数分，绑定实际客户、账户、收款账户、金额及描述中的本地请求引用。HTTP写入前另存传输台账，响应丢失后只查询原记录，不能再次POST。
- **账户事实**：余额使用核心`summary.availableBalance`，不把账面总额当可用额；累计额从有界分页转账记录按账户与日期求和，已撤销记录不计。分页不完整/超过1000条、错币种/账户/金额、未知结果均停止采信；它是小规模演示接口，不是大规模银行分页性能承诺。
- **账户转账与卡管分开**：该实例没有银行卡挂失服务。原预检新增受信账户路径证据：只有已核验本人、活动储蓄账户且明确不支持卡管时，卡检查标为“不适用”；不是伪造银行卡正常。其他未知卡状态仍未知，确认与强认证要求不变。依据`app/preflight.py`及Fineract专项的反例测试。
- **独立环境**：核心和数据库只在内部Docker网络；环回中继供本机访问，核心无公网出口。演示默认口令已轮换为随机口令，虚构客户/账户按实际枚举开户；私有配置不进入Git。仍拒绝APP_ENV=production/live模式；没有真实银行账户、证书、资金或生产认证。

### **6.3 交易、撤销、回调及对账实测**

- **可复用工具**：`scripts/fineract_demo.py`提供start/seed/qa/serve/stop。start只用已缓存的固定镜像，stop只停止指定演示项目并保留卷；seed/serve可在容器内运行，不需要Docker socket。示例：`python scripts/fineract_demo.py qa --directory data/verification/p07-public-20261024/runtime --record data/verification/p07-public-20261024/reusable-core-qa-final.json`。启动新环境先start再seed；不能把本机私有状态文件当作可公开凭据。
- **25项真实核心检查**：`reusable-core-qa-final.json`通过原主链确认前零扣款、确认后付款减少100分/收款增加100分、重复确认拒绝、原生查询、本地/核心引用分离、请求级对账、无假卡管、提现125分及其undo恢复余额、整笔账户转账undo双边恢复、撤销重复请求返回旧回执、原交易reversed、实际原生回调与审计链核对。固定虚构资金，不涉及真实银行。
- **转账undo依据**：所固定版本的`AccountTransfersApiResource`明确实现`POST accounttransfers/{id}?command=undo`；已通过实际调用验证，未仅靠旧版API目录推断。适配器须显式supports_reversal且重新核验原交易，独立幂等键，聊天/DAG不新增自动冲正工具。这个结果只证明该开源核心原生撤销，不证明任一家真实银行支持冲正。
- **回调依据**：`core-reversal-callback.json`和可复用QA记录收到核心Web Hook的ACCOUNTTRANSFER/UNDO。当前上游WebHookService未提供本批验证的机构签名；接收器只记摘要、事件元数据和未受信标记，不直接更新账务。状态以带认证的原生查询为准；不能拿项目HMAC方法冒充供应方签名验收。
- **对账口径**：将平台请求与核心转账记录、撤销状态及付款/收款账户余额核对；不是银行出具的正式对账单，也没有配置完整财务日终总账体系。实际银行凭证/证书、正式对账、卡管、生产IAM和物理异机复验仍未找到通过证据。
- **本批源码与后续交付**：专项5项及实际核心25项记录在上述目录。银行扩展保持8份文件，以预检适配替换原计划的汇总摘要改动；汇总摘要、联合全量及最新离线发行由紧接着的P08批次更新，不能用5.4的旧镜像代表本次源码。
