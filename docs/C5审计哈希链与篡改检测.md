# C5 审计哈希链与篡改检测

> 版本：C5 · 2026-09-21
> 定位：离线可验证的银行生产替身；当前实现不连接真实 WORM、SIEM、KMS 或 HSM。

## 1. 交付边界

C5 为审计事件增加结构化证据字段、全局追加哈希链、链校验接口、篡改告警和高风险操作冻结。SQLite 仅用于单容器演示，不能被描述为银行生产审计中心。

| 演示实现 | 生产替换点 |
| --- | --- |
| `app/banking_agent.py::AuditStore` | 银行审计中心或具备 WORM/Legal Hold 的 append-only 存储；写入账号与业务运行账号隔离 |
| SQLite `audit_events` | 审计事件库、对象存储 WORM 或审计消息总线；要求跨实例顺序、持久化、备份和访问审计 |
| SHA-256 `prev_hash/current_hash` | 生产在哈希链之外增加 KMS/Vault/HSM 托管的 HMAC 或非对称签名，保留密钥版本和验证公钥 |
| `AuditStore.verify_trace(trace_id)` | 独立审计校验服务，定时全库巡检并向 SIEM/SOC 告警 |
| `security.tamper` 与进程内 `frozen_users` | 风控/身份平台的持久化冻结、工单审批和双人解锁流程 |
| `sanitize_audit_value()` | 统一日志网关、字段级脱敏/令牌化服务和数据分级策略；生产禁止在采集前输出原始敏感数据 |

## 2. 结构化事件与哈希链

每个事件包含以下字段：

```text
trace_id, task_id, user_id, device_id, event_type, operation,
risk_level, decision_reason, tool_name, timestamp,
prev_hash, current_hash
```

- `seq` 是单容器演示中的全局追加序号，第一条事件的 `prev_hash` 为 `GENESIS`。
- `current_hash` 是对规范化 JSON 的 SHA-256，输入包含上述业务字段、脱敏后的 `payload` 和 `prev_hash`。
- 事件按全局 `seq` 校验，而不是只按某一条 trace 局部排序，因此可以发现跨 trace 的链断裂。
- 旧版 `event_hash` 保留用于 T5 兼容；新写入同时填充 `event_hash` 与 `current_hash`。
- 写入前完成脱敏，哈希计算和数据库落盘使用同一份脱敏事件，避免“显示值”和“校验值”不一致。

运行时证据位置：

- `AuditStore.write()`：生成结构化事件和哈希链；
- `AuditStore.list_for_trace()`：按 `seq` 返回回放事件；
- `AuditStore.verify_trace(trace_id)`：定位 `break_at`、`break_event_id` 和断裂原因；
- `GET /api/v1/audit/verify?trace_id=...`：对外只读校验入口；
- `GET /api/v1/audit/events?trace_id=...`：返回已脱敏审计事件。

## 3. 篡改检测和冻结流程

当历史事件任一字段被修改时，校验会返回：

```json
{
  "ok": true,
  "valid": false,
  "break_at": 12,
  "reason": "current_hash_mismatch"
}
```

运行时随后：

1. 发布同一 trace 的 `security.tamper` 审计事件；
2. 将断点关联用户加入高风险冻结集合；
3. 用户再次发起红色操作或确认红色操作时返回“检测到审计证据链异常，高风险操作已冻结，请联系人工解锁”；
4. 仅允许明确的人工解锁入口解除演示冻结：`POST /api/v1/audit/unlock`；
5. 校验结果保留断点序号和原因，便于现场演示和取证。

冻结是高风险保护措施，不代表交易已经成功或失败；账务事实仍只能来自核心交易查询结果。

## 4. 脱敏规则

审计写入和输出边界统一执行 `sanitize_audit_value()`：

- 手机号、卡号、身份证号和其他 6–19 位连续数字：保留头 3 位和尾 4 位，中间替换为 `*`；
- 六位验证码：全部替换为 `******`；
- 嵌套字典、列表和元组递归处理；敏感字段的整数验证码也不以明文落盘；
- `payload_json`、结构化列和接口返回都使用脱敏后的值。

生产规则需要覆盖日志参数、异常堆栈、消息队列、指标标签、APM 采样和 SIEM 映射，不能只保护 HTTP 返回体。

## 5. 真实 WORM / SIEM / 密钥替换点

### 5.1 WORM 审计存储

实现 `AppendOnlyAuditSink` 契约，将事件写入银行审计中心或带 Object Lock/Legal Hold 的 WORM 存储。生产要求：

- 业务实例无权更新或删除历史事件；
- 写入具备幂等事件 ID、严格顺序或可验证排序；
- 原始事件、哈希/签名、校验结果和访问记录分别留存；
- 备份、跨地域复制、RPO/RTO、留存周期和销毁审批可追溯。

### 5.2 SIEM/SOC 投递

将 `security.tamper`、认证重放、权限拒绝、账务异常等安全事件投递 SIEM/SOC。生产适配器应提供 mTLS、事件去重、断线重试、死信、告警升级和投递状态查询；不能因为 SIEM 暂时不可用而阻塞核心扣账，也不能静默丢弃安全事件。

### 5.3 KMS/Vault/HSM

当前 SHA-256 链用于离线可验证性，不是密钥签名。生产应由 KMS/Vault/HSM：

- 管理 HMAC/签名密钥、版本和轮换窗口；
- 在事件或批次清单中保存 key version、算法、签名、公钥引用；
- 支持密钥吊销、历史版本验证和双人审批；
- 将签名操作与业务应用权限隔离，定期执行独立校验。

## 6. 验收证据

`tests/test_c5_audit_chain.py` 覆盖：

- 正常哈希链通过 `GET /api/v1/audit/verify`；
- 修改历史事件 payload 后精确定位 `break_at` 和 `current_hash_mismatch`；
- 发布 `security.tamper` 并冻结高风险用户，人工解锁后恢复；
- 审计/接口输出不包含手机号、卡号、身份证号和验证码完整明文；
- 缺少 `trace_id` 的校验请求返回 400。

生产上线前还必须补充独立 WORM、SIEM、密钥服务联调，以及多实例并发追加和灾备恢复演练。


## 7. D2：操作人、账户主体与旧链兼容

- 审计 `actor` 表示当前操作的实际发起人；`user_id` 保持账户主体语义，并通过 `subject_id` 返回同一账户主体。`device_id` 表示本次调用者设备。
- 家庭代办：女儿发起/确认/取消时，`actor` 为女儿，`subject_id` 为父亲；父亲完成强认证时，两者均为父亲。原计划的 `actor_id` 是历史命名的账户主体字段，未改变其扣账、风控及凭证归属含义。
- 认证凭证内的 `binding.user_id/device_id` 仍绑定账户本人及本人设备；不要把审计调用者设备误当成认证凭证的设备。HTTP 身份由服务端会话解析；模型和请求体不能授权自己成为操作人。统一渠道网关仅接受可信适配器转换后的身份。
- 每次 Runtime 操作以请求级 `ContextVar` 传递审计身份；调用结束或异常时复原，避免线程并发与后续请求串号。跨用户拒绝记录真实调用者；未登录拒绝记为 `anonymous`，而不是冒记账户本人或守护人。
- 新事件在已参与哈希的 `payload._identity` 内固定 `actor_id/subject_id/device_id`，覆盖调用方传入的同名 envelope。校验同时比对数据库身份列与该 envelope，因此只篡改 `actor` 列也会断链。旧事件不补写、不重算哈希，仍按原算法验证；旧事件未被保护的历史 `actor` 字段不能通过升级追溯获得完整性保证，也不会推测恢复当时的真实操作人。
- 后台账务对账记录为 `system:recovery`，审计篡改保护动作记录为 `system:audit-verifier`；关联账户仍保存在 `subject_id/user_id`。家庭代办链断裂冻结账户主体，不因操作人是守护人而错误冻结守护人账户。
- 验证入口：`tests/test_d2_actor.py` 覆盖家庭查询、本人认证、重启后代办确认、取消、跨用户/匿名拒绝、并发身份隔离、异常清理、身份列篡改、旧链兼容及后台对账。

以上仅为演示级证据准确性增强，不替代真实 IAM、可信设备证明、WORM 或独立审计签名。
