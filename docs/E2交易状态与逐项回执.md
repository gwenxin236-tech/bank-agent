# E2 交易状态与逐项回执

## 1. 目的与边界

本阶段增加的是**用户回执视图层**，不是新的账务状态机，也不改变 D6 DAG 调度器。它读取已经持久化的交易/DAG 结果，把“处理中、结果未知、明确失败、部分完成”等机器事实转换为可核对的用户语言。

- `app/transaction_views.py` 只读 DAG/交易快照，不调用工具、不授予权限、不重试副作用。
- 真实银行核心或支付网关的状态码，生产时应由 Adapter 先归一化，再交给本视图层；本项目的 MockBankCore 仅用于离线演示。
- `结果未知` 不等于失败，也不等于成功。正确动作是查询原幂等请求；禁止因为通信超时而再次提交转账。
- 人工接管在本项目中仍是演示级流程，不宣称已经连接真实客服系统或银行核心。

## 2. 面向用户的交易状态映射

| 核心/工具事实 | 用户状态 | 用户文案 | 下一步 |
| --- | --- | --- | --- |
| `processing` | 处理中 | 银行还在确认这笔交易，请不要重复操作 | 等待或查询原交易 |
| 传输超时、网络不可达、工具无法证明结果 | 结果未知 | 结果未知，正在核验这笔交易，请不要重复操作 | 查询原幂等请求，不自动重发 |
| `succeeded` / `success` | 已完成 | 这笔交易已完成 | 以工具返回的交易号和账务结果为准 |
| `failed` | 明确失败 | 银行已明确返回失败，这笔交易未完成 | 按失败原因处理，不把它说成成功 |
| 多步骤中既有已完成又有失败/未执行 | 部分完成 | 这项任务部分完成，请查看逐项回执 | 逐项核对，必要时转人工 |
| `reversed` | 已冲正 | 这笔交易已冲正，请以银行账务记录为准 | 核对冲正流水 |

其中，`processing` 表示核心已经给出处理中语义；`结果未知` 表示本次提交的传输链路没有得到足够证据确认结果。两者都不能被用户界面渲染成“已完成”。

## 3. DAG 逐项回执

`dag_receipt()` 只读取 `TaskDag.nodes` 及节点的执行/补偿证据，输出 `items` 和独立的 `compensations` 区域。

| DAG 节点事实 | 回执状态 | 含义 |
| --- | --- | --- |
| 节点 `succeeded` 或已完成补偿的节点 | `COMPLETED` / 已完成 | 该步骤有明确成功结果；不能被后续失败覆盖 |
| 节点 `running` 且结果未知/处理中 | `PENDING_VERIFICATION` / 已执行待核验 | 已发起但尚未取得终态，只能核验原请求 |
| 节点 `failed` | `FAILED` / 明确失败 | 该步骤明确失败，不伪装为成功 |
| 节点 `pending`、`ready`、`skipped` | `NOT_EXECUTED` / 未执行 | 没有形成成功副作用 |
| 补偿结果 `succeeded` | `COMPENSATED` / 已完成补偿 | 补偿单独展示，不覆盖原步骤回执 |
| 补偿结果未知/处理中 | `COMPENSATION_PENDING_VERIFICATION` / 补偿待核验 | 补偿已发起但不能宣称完成 |

因此，一个任务即使整体进入 `failed`，也会继续展示已经完成的节点、明确失败节点、未执行节点以及补偿动作；不会用一个“失败”覆盖已经发生的有效步骤。前端 `app/static/app.js` 复用现有 `result_view`，在结果卡中渲染“逐项办理回执”和“补偿动作”。

## 4. 与调研报告 §11.4 十状态对照

| 报告十状态 | 当前项目映射/实现 | 说明 |
| --- | --- | --- |
| 草稿 | 计划生成前后的 AgentPlan | 现有计划卡展示；不代表已授权 |
| 待澄清 | `awaiting_details` / 澄清计划 | 缺少收款人或金额时先补充信息 |
| 待授权 | `requires_confirmation` | 用户确认前不得产生副作用 |
| 已授权未提交 | consent/强认证通过、工具尚未提交 | 由确认入口与一次性凭证约束 |
| 已提交/受理 | 核心交易 `created` | 通过 MockBankCore 的交易记录保留幂等键 |
| 处理中 | 核心 `processing`，视图 `PROCESSING` | 用户看到“银行还在确认” |
| 结果未知 | 传输超时/不可达的视图 `UNKNOWN`，DAG 节点保持运行待核验 | 只查询原请求，不自动重发；这是 E2 阶段 1新增路径 |
| 已完成 | 核心 `succeeded`，节点 `succeeded`/`compensated` 的已完成回执 | 数字和交易号只能来自工具结果 |
| 明确失败 | 核心 `failed` 或 DAG 节点 `failed` | 保留错误事实和审计证据 |
| 已取消/授权已撤销 | 现有 cancel、授权撤销/过期路径；DAG 可进入 `cancelled` | 已发生的不可逆转账不因界面取消而虚构冲正 |
| 部分完成/转人工 | DAG 回执 `PARTIAL`；人工接管为现有演示级路径 | 逐节点展示，必要时转人工；真实客服接入是生产替换点 |

报告列出十类业务状态，其中“部分完成/转人工”可同时作为任务结果和处置建议；本项目不把人工接管渲染成银行交易成功。

## 5. 证据链与测试

- `tests/test_unknown_and_partial_receipts.py` 验证超时/不可达进入结果未知、重启后仍查询原请求、余额不重复扣减、审计记录 `transaction.unknown`。
- `tests/test_e2_partial_receipts.py` 验证 DAG 失败时已完成/明确失败/未执行节点不被覆盖，补偿动作独立展示，结果视图不会把部分完成说成整体成功。
- `tests/test_dag_integration.py` 继续覆盖真实 Agent/DAG 主链、持久化、暂停恢复和幂等副作用边界。

## 6. 生产替换点

1. 用真实核心 Adapter 的交易查询接口替换 MockBankCore 查询，但保留同一幂等键和“未知不得重发”策略。
2. 用生产事件总线/审计 WORM 或 SIEM 接入替换离线 AuditStore；回执仍只读取经过权限校验的事实快照。
3. 用真实客服工单/人工坐席系统替换演示级 human handoff，并由生产权限系统重新校验操作者和授权范围。
4. 在生产环境补充跨系统一致性、重复消息、查询超时、补偿失败和灾备恢复的独立验收，不以本项目离线演示等同生产银行灾备验收。
